# Case021 — 같은 INT4 가중치인데 왜 계산 결과가 달라질까?

[English](README.md) · [상세 보고서](REPORT.ko.md) · [CPU 검산](REPRODUCE.ko.md)

**같은 4비트 숫자를 저장해도, 복원할 때의 반올림과 GPU 계산 경로가 달라지면 최종 출력이 달라졌습니다.** Q/K norm–RoPE의 중간 계산을 FP32로 유지해도 두 실행 경로의 불일치가 일관되게 줄지는 않았습니다.

가중치는 모델이 계산에 사용하는 숫자입니다. INT4는 이를 4비트 정수로 저장하는 방식이고, scale은 정수를 실제 계산 크기로 되돌리는 배율입니다. 이번에는 기존 Qwen3-0.6B의 같은 D16 artifact를 사용했습니다. 새로 양자화하거나 학습하지 않았습니다.

| 경로 | 쉬운 설명 |
|---|---|
| D0 | 원래 순서대로 가중치를 복원한 뒤 dense 계산 |
| D1 | Marlin에 전달하는 BF16 scale 형식에 맞춰 복원한 뒤 dense 계산 |
| P | 같은 정수와 scale을 packed 형태로 넣어 실제 Marlin 계산 |

D0–D1은 복원 산술과 scale 표현의 차이, D1–P는 형식을 맞춘 뒤에도 남는 실행 차이입니다. D1은 과거 Case013에도 있던 대조이며, 새 양자화 기법이 아닙니다.

Attention은 토큰 사이의 관계를 계산합니다. 그 앞에서 Q/K 벡터의 크기를 정리하고 위치를 반영하는 부분이 Q/K norm–RoPE입니다. **R0**는 기존 HF 계산, **R1**은 이 부분의 중간값만 FP32로 유지합니다. 두 경우 모두 attention에 넘기는 Q/K는 BF16입니다.

주 결과는 EVAL 24문서의 512-token 입력에서, 문서마다 미리 정한 16위치의 전체 어휘 분포를 비교한 것입니다. KL은 두 확률 분포의 차이를 나타내며, 여기서 작은 값은 모델 품질이 아니라 **두 경로의 출력이 더 비슷함**을 뜻합니다.

| 관측 | 결과 |
|---|---:|
| D1–P 평균 KL, R0 → R1 | 0.00069525 → 0.00078153 |
| 불일치가 줄어든 / 늘어난 문서 | 9 / 15 |
| 평균 감소량 E0−E1의 95% 구간 | −0.00020682 ~ +0.00003909 |

구간에 0이 들어 있어 판정은 **INCONCLUSIVE: 감소·증가 방향을 확정하지 못함**입니다. 정밀도를 높이면 각 계산이 더 정확해질 수 있지만, 서로 다른 두 실행 결과 사이의 거리가 반드시 줄어드는 것은 아닙니다.

![문서별 R0/R1 차이](figures/02_rounding_discrepancy.png)

그림의 선 하나가 문서 하나입니다. 오른쪽 패널은 고정 D0_R0에 대한 차이이므로 왼쪽의 D1–P 비교와 기준이 다릅니다.

같은 입력을 선택한 두 층에 다시 넣어 보니, scale 표현 차이와 실제 실행 차이가 모두 남았습니다. DEV에서 고른 25번 층의 출력만 교체한 EVAL 진단도 10문서에서는 차이를 줄이고 14문서에서는 늘렸습니다. 이를 개선법으로 추천할 근거는 얻지 못했습니다.

이 사례가 주는 선택 기준은 **저장된 정수·scale, 복원 산술, 실제 backend, 이후 계산을 따로 확인해야 한다**는 것입니다. dtype 이름이 같다는 사실만으로 두 경로가 같다고 볼 수 없습니다. 구현·검산·원자료를 함께 남겨 차이를 다시 살펴볼 수 있게 했습니다.
