# Case018 — 복구한 AI는 다음 업무도 제대로 수행할 수 있을까?

재고를 잘못 옮긴 뒤 수량을 되돌려도, 처리 중 표시가 남아 다음 이동이 막힐 수 있습니다. 이 작은 합성 환경은 **복구 선언**, **실제 수량 복원**, **복구 뒤 업무 결과**를 나눠 검사합니다. 영문 이름은 *State Recovery and Continuation Bench*입니다.

이번 구현은 P0 CPU 준비입니다. 모델 대신 고정 프로그램으로 도구를 호출해 실행기와 평가기를 검사했습니다. 모델 성공률·가드 효과·KV 품질 차이는 아직 측정하지 않았습니다.

업무는 창고 재고와 처리 원장 하나입니다. 잘못된 대상 수정(A), 정상 1회 이후 중복 실행(B), 일부만 실행된 이동(C)을 각각 두 개씩 만들었습니다. A/C는 오류 효과를 되돌리고 원래 작업을 후속 절차에 남깁니다. B는 정상 1회 효과를 보존합니다. 수량 보상과 처리 원장 해제는 별도 공개 도구이며, 자동 정답 복구 API는 없습니다.

평가기는 종료 상태의 복제와 참 checkpoint의 복제에서 같은 두 후속 절차를 실행합니다. 현재 수정 번호는 매번 공개 read로 얻습니다. 이 후속 작업은 모델의 자율 행동이 아니라 고정 CPU 프로그램입니다. 두 경로는 각각 독립 복제에서 시작합니다.

Q는 **종료 상태·후속 업무 적합**, W는 **검증된 복구 workflow 완주**입니다. 수량이 맞고 후속 업무가 성공해도, 마지막 변경 뒤 성공 검증을 관측하지 않았거나 최종 응답이 없으면 Q=1/W=0이 가능합니다. 공개 validator의 `valid:true`도 checkpoint 복원을 보증하지 않습니다.

향후에는 동일 BF16 가중치에서 BF16/NVFP4 KV와 기본 종료(R0)/최신 검증 완료 가드(R1)를 비교할 계획입니다. 모든 조건에 공통 JSON 문법을 사용합니다. **이번에는 모델·tokenizer·문법 backend·native KV를 실행하지 않았고 HOLDOUT 입력/정답도 만들지 않았습니다.** P1 확대에 모델 성공률 임계값은 없으며 `model_success_threshold=null`로 명시했습니다. 기존 Case017의 이탈을 소급 정당화하는 변경이 아닙니다.

원리 참고는 ReTrace의 복구 뒤 결과 확인과 ACE-Compression의 개별/동시 제약 평가입니다. GUI 에이전트·원 논문의 실험·새 알고리즘을 재현했다고 주장하지 않습니다. 코드 작성에는 Codex의 지원을 받았습니다. 직접 구현한 부분은 합성 상태·보상 도구·관측 추적·가드·CPU 평가/감사 경로입니다.
