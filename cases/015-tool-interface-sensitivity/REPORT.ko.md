# Case015 — 같은 도구, 다른 이름

## 요약

AI가 사용하는 도구의 이름만 바뀌면, 같은 일을 끝까지 해낼 수 있을까요? 이 연구에서는 조회·계산·저장 기능을 AI에게 제공하고, 기능은 그대로 둔 채 이름 표기만 바꾸어 작업 결과를 비교합니다.

구체적인 예제는 **구매 내역의 총금액을 계산해 기록하는 일**입니다. AI는 구매한 개수와 개당 가격을 조회하고, 둘을 곱한 금액을 저장한 뒤 제대로 기록됐는지 확인해야 합니다. 이 흐름을 실행하고 결과를 다시 검사하는 도구를 구현했습니다.

작업 예제와 용어는 [쉬운 안내](README.ko.md)에서 먼저 읽을 수 있습니다.

비교한 모델은 같은 Qwen3-4B의 세 가지 표현입니다. **BF16**은 원래 16비트 모델, **RTN**은 단순 반올림으로 가중치를 4비트 저장한 기준선, **D16**은 DualQuant 공개 수식 기반으로 가중치를 4비트 저장하고 중간 계산값은 16비트로 유지한 비교 조건입니다. 압축 저장본은 BF16으로 복원해 작업 수행 품질을 측정했습니다.

A1은 아래의 새 구매 금액 기록 시험이고, P1은 앞서 수행한 이름·순서 변경 시험입니다. 두 단계의 결과는 따로 표시합니다.

<a id="section-1"></a>
## 1. 배경

같은 기능도 이름이 바뀌면 AI가 다르게 호출할 수 있습니다. 기존 P1은 길게 주어진 입력에서 이미 관측한 문제 8개(개발용 자료, DEV)의 도구 이름·목록 순서를 바꾸어 성공→실패와 실패→성공을 비교했습니다. A1은 그 결과를 본 뒤 설계한 새 응용시험이며 실제 회사나 결제 시스템에 연결하지 않았습니다.

<a id="section-2"></a>
## 2. 질문과 가설

주 질문은 원래 이름(API_V1)과 바꾼 이름(API_V2)에서 같은 문제가 둘 다 성공했는지, 성공→실패 또는 실패→성공으로 바뀌었는지입니다. API는 AI가 기능을 이름과 입력값으로 요청하는 연결 방식입니다. 새 이름이 더 좋아야 한다는 방향은 정하지 않았습니다. D16의 성공 변화에서 BF16의 성공 변화를 뺀 값은 보조로 계산했습니다.

<a id="section-3"></a>
## 3. 원리와 실행 계약

1. **구매 정보 확인:** 지정된 구매 내역에서 개수와 개당 가격을 읽습니다.
2. **총금액 계산:** 조회 결과를 받은 다음, 곱셈 도구에 두 숫자를 전달합니다.
3. **금액 저장:** 계산 결과를 받은 다음, 해당 구매 내역의 총금액을 수정합니다.
4. **저장 결과 확인:** 올바른 금액인지 확인하는 도구를 실행합니다. 다른 구매 내역은 바꾸면 안 됩니다.
5. **완료 보고:** 확인 결과를 받은 뒤, 구매 ID·총금액·확인 여부를 정해진 형식으로 답합니다.

실제 쇼핑몰과 연결하지 않고 실험용 JSON 파일로 시험했습니다. JSON은 항목 이름과 값을 짝지어 저장하는 텍스트 형식입니다. 초기 요청에는 개수와 가격을 넣지 않았으므로 AI가 조회 도구의 결과를 받아야 합니다. 금액은 소수점 없는 정수 단위로 다룹니다.

| 처음 보는 표현 | 이 사례에서의 뜻 |
|---|---|
| 주문 / order | 구매 내역 한 건. 기록의 `order_id`는 그 내역을 구별하는 ID입니다. |
| 수량 / 단가 | 구매한 개수 / 물건 하나의 가격입니다. |
| 도구 호출 / API | AI가 조회·계산 같은 기능을 이름과 입력값으로 요청하는 방식입니다. API 이름은 그 기능을 부르는 이름입니다. |
| 시나리오 / fixture | 시험할 문제 한 개 / 그 문제에서 사용하는 초기 실험용 파일입니다. |
| episode | 초기 파일에서 시작해 AI가 답을 마칠 때까지의 실행 한 번입니다. |
| 관측 이력 | AI가 다음 응답을 만들기 **전에 이미 받은** 도구 결과입니다. 파일이 바뀌었다는 사실과 구분합니다. |
| 회귀 / 회복 | 이름 변경 전에는 성공했지만 이후 실패 / 이전 실패가 이후 성공으로 바뀐 경우입니다. |

코드의 `quantity`, `unit_price_minor`, `total_minor`는 각각 개수, 정수 단위의 개당 가격, 총금액입니다. 코드·원기록의 필드명은 유지합니다.

도구의 이름 표기 두 가지를 **API_V1(원래 이름)**과 **API_V2(바꾼 이름)**로 부릅니다. 예를 들어 구매 내역을 읽는 `read_order`를 `readOrder`로 바꿉니다. 기능·설명·입력값 형식·목록 순서는 같습니다.

아래의 의미 ID는 같은 기능을 추적하는 내부 표식이며 AI에게 보여주지 않습니다.

| Semantic ID | API_V1 | API_V2 |
|---|---|---|
| order.read | read_order | readOrder |
| amount.multiply | multiply_amount | multiplyAmount |
| order.write | write_order_total | writeOrderTotal |
| order.validate | validate_order | validateOrder |

AI의 응답 하나에 여러 호출이 들어 있으면 모두 **그 응답을 만들기 전** 받은 결과만 이용한 것으로 기록합니다. 조회 결과를 받은 다음 응답에서 곱셈을 요청하고, 곱셈 결과를 받은 다음 응답에서 저장을 요청해야 합니다. 저장과 확인은 같은 응답에 있어도 순서대로 실행하면 허용합니다. 마지막 완료 답변은 현재 파일의 확인 결과를 실제로 받은 뒤에 해야 합니다. 이것이 여기서 말하는 ‘관측 계약’입니다.

<a id="section-4"></a>
## 4. 방법

주 성공 기준인 `VERIFIED_WORKFLOW_SUCCESS`는 위 다섯 단계의 완료 여부입니다. 실제 총금액이 맞고, 다른 구매 내역과 수정하면 안 되는 항목이 전 과정에서 보존돼야 하며, 마지막 답변의 구매 ID·정수 금액·확인 여부도 정확해야 합니다. 참/거짓(bool)을 금액 정수와 같은 값으로 취급하지 않습니다. 입력 형식(schema)이 맞으면 잘못된 숫자도 그대로 계산·저장합니다. 별도의 정답 검사기(oracle)가 모델의 입력값을 고쳐주지 않습니다. 마지막 파일 값만 맞았는지(`STATE_ONLY_SUCCESS`)와 최종 답변만 맞았는지(`FINAL_ANSWER_CORRECT`)도 따로 기록했습니다.

<a id="section-5"></a>
## 5. 실험

고정 난수값(seed) 6101621로 영어 지시문 4개에 각각 실험용 파일 4개를 배정해 16개 문제를 만들었습니다. 사전 작동 확인용 파일(smoke)은 별도 1개입니다. 구매 ID와 금액은 독립 생성했습니다. 개수는 2..40, 개당 가격은 100..20,000의 정수이고, 초기 총금액은 미기록(null) 또는 잘못된 값(-1)입니다. 초기 요청에는 개수와 가격을 보여주지 않습니다. 토큰 길이는 506..518로 기존 P1의4K/8K와 다릅니다. 16×2API×3방법=96 본 episode, BF16 두 API smoke2를 별도 실행했습니다. 순서 seed6101622와 BF16→D16→RTN을 등록했습니다.

같은 revision cdbee75f17c01a7cc42f958dc650907174af0554, greedy192token, enable_thinking=False, 최대8모델 요청·6도구 시도·900초, context24576, BF16/SDPA, logits_to_keep=1, within-request KV ON/turn cache OFF입니다. ENUM·추가 feedback·alias는 OFF. 252개씩의 원 RTN/D16 저장본을 읽었고 D16 beta_inverse/W_pre 경로를 유지했습니다.

## 6. 결과

### A1 — 새 구매 금액 기록 시험

각 칸은 16개 문제 중 성공한 개수입니다. 원래 이름 V1과 바꾼 이름 V2는 같은 기능의 두 이름 표기입니다.

| Model | API_V1 verified /16 | API_V2 verified /16 | Both success | Loss | Gain | Both fail |
|---|---|---|---|---|---|---|
| BF16 | 15 | 16 | 15 | 0 | 1 | 0 |
| RTN | 16 | 16 | 16 | 0 | 0 | 0 |
| D16 | 12 | 12 | 12 | 0 | 0 | 4 |

보조 비교인 D16−BF16 성공 변화 차이는 -6.25퍼센트포인트(pp), 95% 탐색 구간(CI)은 [-18.75, +0.00]pp입니다.

구간은 영어 지시문 표현 4개의 묶음을 유지해 10,000번 다시 뽑는 계산(bootstrap)으로 구했습니다. 고정 난수값은 6101623입니다. 이 네 표현과 이름 변경 한 가지의 불확실성을 보여주는 탐색 결과입니다.

### P1 — 앞서 수행한 이름·순서 변경 시험

8개 기존 문제에서 원형(I0), 목록 순서 변경(I1), 이름 표기 변경(I2), 의미를 드러내지 않는 이름(I3)을 비교했습니다. 각 칸의 분모는 8입니다.

| 기존 P1의 작업 | AI에게 요구한 일 | 원 문제 ID |
|---|---|---|
| 문서 읽기 | 문서에서 장소 이름과 담당자 정보를 읽어 답하기 | AGENT-0/1 |
| 조회 후 계산 | 기록에서 개수와 개당 가격을 읽어 곱셈 도구로 총금액 계산하기 | AGENT-2/3 |
| 최신 정보 찾기 | 이전·현재 상태 표에서 최신 상태를 찾아 답하기 | AGENT-4/5 |
| 설정 수정·확인 | 실험용 설정 파일의 두 값을 바꾸고 확인 도구 실행하기 | AGENT-6/7 |

| Model | I0 original /8 | I1 order /8 | I2 lowerCamel /8 | I3 opaque /8 |
|---|---|---|---|---|
| BF16 | 8 | 8 | 8 | 7 |
| RTN | 8 | 8 | 8 | 8 |

원 P1 주 interaction +8.33pp, 95% CI[-8.33,+25.00]pp; 손실과 회복을 별도 보존했습니다. 두 단계의 96개를192개의 같은 점수로 합산하지 않습니다.

### 비용

전체 실행 시간 687.452초. 본시험은 모델 응답 요청 463회, 도구 호출 시도 378개, 파싱 가능한 호출 사건 368개(거절된 구매 ID 1개 포함), 성공한 도구 반환 367개, 생성 토큰 16,927개입니다. 별도 사전 작동 확인은 요청 10회·도구 8개·토큰 360개입니다. Torch가 기록한 GPU 메모리 최고값은 할당 7.802 GiB / 예약 8.021 GiB입니다.

Worker wall은 모델 hash·load·decode·smoke·실패·I/O를 포함합니다. Torch allocator peak와 Windows 배경 사용을 구분한 장치 free/total 표본을 응답별로 남겼습니다. serving 속도나 native INT4 가속 측정이 아닙니다.

## 7. 실패와 회복 분석

BF16 / A1-06: V1은191444를 올바르게 저장했지만 validate_order의 주문 ID를 ...3657 대신 ...3659로 생성했습니다. 오류 결과를 받고 validated:false로 끝났습니다. V2는 원 대상 ID로 검증하고 성공했습니다. D16은 A1-00/06/08/14에서 두 API 모두 write 호출 JSON을 완성하지 못해 저장 전에 끝났습니다. 미등록 이름과 관측 순서 위반은0건입니다. API 변화가 D16의 이 parse 실패를 회복시키지 않았습니다.

기록 결함을 사후 주석으로 분리했습니다. malformed-only 응답에서 조기 종료한8건의 원 terminal_reason은 초기값 BUDGET_EXHAUSTED로 남았으나 실제 모델/도구 예산은 소진하지 않았습니다. 별도 주석은 PARSE_ERROR로 설명합니다. 잘못된 주문 ID1건은 원 summary의 ARGUMENT_VALUE_WRONG에 빠졌지만 원 tool event에 UNKNOWN_ORDER/BAD_ARGUMENTS로 남아 있어 주석에서 값 오류로 집계합니다. 원 응답·코드 동결·성공 판정은 그대로이며 독립 endpoint 재계산의 영향은0건입니다. 조기 parse-only 종료 후의 recovery는 관측하지 않았습니다.

P1은 실행 직전 같은 fixture와 생성 전 같은 관측을 별도로 고정하지 않았습니다. 새 표시 계층은 그 둘을 구분하며 A1 계약으로 옛 점수를 고치지 않습니다.

<a id="section-8"></a>
## 8. 결론

한 주문 워크플로에서 이름 변경 회귀를 추적·재실행하는 도구를 완성했습니다. API_V2에서 손실은 없고 BF16 회복1건이 있었지만, D16의4개 fixture 실패는 남았습니다. 기존 P1의 인터페이스 민감도와 같은 현상으로 단정할 수 없습니다. 다음 연구는 P2 복구 진단을 별도 승인·등록하고 동일 관측을 주는 대조를 포함하는 것입니다.
