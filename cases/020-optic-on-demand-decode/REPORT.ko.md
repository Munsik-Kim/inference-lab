# Case020 — 작은 임베딩 저장과 실행 비용을 함께 비교했습니다

[English](REPORT.md) · [첫 설명](README.ko.md) · [CPU 재현](REPRODUCE.ko.md)

## 1. 질문과 실제 관측

“임베딩을 작게 보관하면 실행도 빨라질까?” 같은 압축 표현을 세 방식으로 실행했다. B는 A보다 상주 tensor와 할당 최대값이 작았다. 그러나 같은 process에서 호출 순서를 교차한 P4의 C/B30개 비교 block에서는 C의 속도 이득이0/30이었다. 준비와 실제 호출을 함께 재면 짧은 세션에서는 A/B의 순서가 섞였고, N1024·4096에서는 A가 모든 block에서 빨랐다. 원 측정은 RTX5080/sm_120, Python3.12.14/Torch2.13.0+cu130/CUDA13.0/driver621.01이다. 이번 게시 작업은 저장 자료를 CPU로 다시 계산했다.

## 2. 방법과 같은 출력 계약

| 방법 | 하는 일 | 호출 사이에 남는 것 |
|---|---|---|
| A · 전체를 미리 계산 | 같은 압축 표현의 모든 항목을 계산한 뒤 번호로 조회 | 큰 재구성 표 |
| B · 요청한 항목만 계산 | 공식 복원 코드로 요청한 M개를 계산 | 작은 코드·사전·복원 계산 값 |
| C · 중복 항목은 한 번만 계산한 뒤 원래 순서로 복구 | 매번 중복을 찾고 U개 계산 후 M개로 되돌림 | B와 같은 작은 자료 |


M은 요청한 번호 수, U는 실제로 서로 다른 번호 수다. 요청 번호·artifact·device·BF16 출력·모든 layer·raw unscaled 순서를 같게 했다. 출력 `[M,L*H]`는 `[M,L,H]` 순서로 읽는다. A는256행 chunk로 공식 decoder를 호출해 전체 표를 만들고 구축용 compact module을 제거한다. B는 고정 upstream의 수정 없는 forward다. C는 매번 `torch.unique(sorted=True,return_inverse=True)`→U행 decoder→inverse gather를 수행하며 결과 M행을 반환한다. 사전 unique 계산이나 반복 간 cache는 없다.

S는 Z32/M2048/U2048에서만 ID 정렬→M행 복원→원 순서 복귀를 수행한 진단 대조다. 복원 행을 줄이지 않으며 중복 제거 최적화가 아니다. S/B1.763과 C/S1.133은 각각 block별 짝 비율의 중앙값이다. 두 중앙값을 나눠 다른 비교를 만들지 않는다. C와 S의 정렬·할당·호출 구성이 달라 C−S를 unique의 순수 인과 비용으로 부르지 않는다.

## 3. 원 P2: 방법을 따로 둔 메모리

LARGE/Z32/M2048/U512의 세 block에서 아래 값이 같았다. MiB는2^20 bytes다. 이 표는 원 P2 method별 독립 process의 결과다. P4에서 A와 compact module을 함께 둔 process 메모리는 섞지 않았다.

## 5. 중간 벡터 폭과 실제 저장량

Z는 복원 계산에 쓰는 중간 벡터의 폭이다. V32768/L16/H256/K256/group_width4를 유지하고 groups는 Z/4로 바뀐다. 아래의 실측 열은 저장 raw의 실제 module buffer inventory에서 A table과 공통 ID를 빼고 dtype·shape·alias를 검사해 고유 storage를 합했다. NPZ 배열도 `allow_pickle=False`로 읽었다. 이론식을 실측 열에 복사하지 않았다.

|---|---|---|---|---|---|---|---|---|
| 32 | 8 | 550998 | 548864 | 548928 | 548928 | 18 | 0.5235 | 489.02 |
| 128 | 32 | 2173022 | 2170880 | 2171136 | 2171136 | 6 | 2.0706 | 123.64 |
| 644 | 161 | 10891362 | 10889216 | 10890504 | 10890504 | 6 | 10.3860 | 24.65 |


이론식은 `V*G + 2*K*Z + 2*L*H*Z + 2*L*H + 8*G`다. 끝 항은 non-persistent group_offsets도 실제 메모리를 쓰기 때문에 포함했다. 폭별 실제 inventory18/6/6개가 각각 같은 저장량을 보였다. dense 표는256MiB다. Z32의 약489배를 Z644 또는 학습된 모델에 적용하지 않는다. Z644/U512의 C/B1.142는 더 작은 상대 손해지만 여전히 C가 세 block 모두 느렸다. 폭 변화는 groups·codebook·상주량·연산량도 바꾸므로 Z 하나의 순수 효과가 아니다. Z644는 원문 E4B의 latent 폭만 대응하고 전체 shape나 품질을 재현하지 않는다.

## 6. 첫 호출과 실제 N회 누적 비용

대상은 Z32/M2048/U512다. A/B/C×N128/1024/4096×3 block=27개 fresh process다. warm-up 없이 첫 cold 호출도 N에 넣었다. setup은 artifact 읽기/전송·ID 읽기/H2D·A의 전체 표 생성과 compact 정리를 포함한다. session은 자료 읽기 전부터 N회 동기 호출과 소유 tensor 최종 정리까지다. 전체 worker는 Python 시작·공통 CUDA 초기화·결과 기록·종료까지 parent에서 재었다. session은 전체 worker의 일부, first call은 loop의 일부이며 중복 가산하지 않는다.

## 7. 공통32MiB의 발생 단계

원90개 최종 raw는 artifact/ID 전에 공통 library 초기화를 마친 baseline이 이미32MiB였다. warm−baseline−module−ID 잔여는0–952 bytes다. 원 after-load/output-release endpoint나 allocation stack은 없었다. 새 P4 A/B/C3개 진단에서는 context 직후0→작은 FP16 GEMM 뒤32MiB→module/ID 제거 뒤32MiB였다. 남은 active block의 stack에서 `setWorkspaceForHandle`, `getCurrentCUDABlasHandle`, FP16 cuBLAS GEMM helper를 확인해 **새 replay의 Torch cuBLAS handle workspace**로 attribution했다. 과거 allocation의 stack까지 읽었다고 소급하지 않는다. [새 단계값](summary/memory_stages.csv)과 [원 P4 stack raw](publication/originals/pre-publication/followup/p4_speed_cost/results/p4-20261026-1451/memory_B.json)을 연결한다.

## 8. 검증·분모·이력·재현

원 P2 최종은10입력×3방법×3 block=90 cell-block이다. 순서 이탈이 있던 첫90개는 diagnostic으로 별도 보존했다. 원 host C 승리5/30, event mean4/30, 교집합0/30이다. host 승리 중3개는 U=M이었다. 결과를 삭제하거나 새 결과에 합치지 않았다. P4 core3입력×6 block과 width4입력×3 block은 C/B30비교이며 독립 workload30개가 아니다. timing30 worker·96 method-block, lifecycle27 worker, preflight3+smoke1+memory3을 더해 신규64 worker다. GPU 실패/재시도/누락0, profile0이었다.
