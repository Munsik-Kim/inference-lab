<a id="llm-transformer"></a>
## LLM과 Transformer

LLM은 많은 텍스트로 학습해 글의 점수를 계산하거나 글을 생성하는 언어 모델입니다. 단어나 단어 일부가 될 수 있는 텍스트 단위인 토큰(token)을 처리합니다. Qwen은 정보를 조합하는 attention과 순방향 계산 블록인 MLP를 반복해 토큰의 숫자 표현을 바꾸는 Transformer 구조를 사용합니다.

[관련 사례 006](CASEBOOK.md#case-006).

<a id="inference"></a>
## 추론(inference)

이미 학습된 모델을 실행해 점수나 출력을 얻는 과정입니다. 이 사례들은 새 모델을 학습하는 대신 실행 방식이나 계산을 바꾸어 비교합니다.

[관련 사례 001](CASEBOOK.md#case-001).

**저장한 모델 파일: artifact·checkpoint·재로딩**

모델 변환 이야기에서 artifact는 변환해 저장한 모델 파일입니다. 가중치 배열·설정·읽는 데 필요한 정보를 포함합니다. Checkpoint는 모델 상태를 저장한 파일이고, 재로딩(reload)은 다시 읽는 일입니다. 새 프로세스 검사는 별도 프로그램을 시작해 제작 때 남은 메모리 덕분에 잘못된 저장본이 작동하는 일을 막습니다. 다른 문맥의 artifact는 저장한 결과 파일일 수도 있으므로 대상을 함께 표시합니다.

[Case008 저장·재시작](CASEBOOK.md#case-008).

<a id="quantization"></a>
## 양자화(quantization)

숫자를 제한된 값들로 표현하는 방법으로, 흔히 비트 수를 줄입니다. 저장량이나 계산 비용을 줄일 수 있지만 표현값이 달라지며, 실제 속도는 지원되는 실행 경로에도 달려 있습니다.

[관련 사례 002](CASEBOOK.md#case-002).

**참조 계산(reference)과 압축 상태 실행(packed)**

Reference는 비교 기준으로 명시한 계산입니다. Case013·후속 연구와 Case014에서는 압축한 숫자를 BF16으로 복원한 뒤 행렬을 계산해 품질을 확인합니다. Packed 저장은 적은 비트의 값 여러 개를 함께 담는 것으로, 예를 들어 한 바이트에 INT4 두 값을 넣습니다. 그 압축 표현을 GPU 연산에서 직접 처리하는 실행은 별도 경로입니다. 저장과 참조 품질 검사를 통과해도 압축 상태의 요청 처리가 빨라졌다는 뜻은 아닙니다.

[Case013 검사와 한계](CASEBOOK.md#case-013).

<a id="number-formats"></a>
## 숫자 형식 BF16·FP8·INT8

숫자를 표현하는 형식의 이름입니다. BF16·FP8은 16비트·8비트 부동소수점, INT8·INT4는 8비트·4비트 정수 형식입니다. FP32·FP64는 32비트·64비트 부동소수점입니다. 형식마다 범위와 값 사이 간격이 다릅니다. 모델이 학습한 값인 가중치(weight)와 각 연산에 들어가는 값인 활성값(activation)은 다른 형식을 쓸 수 있습니다. W4A16은 4비트 가중치·16비트 계산 입력을 뜻하며 실제 숫자 형식과 구현도 함께 확인해야 합니다.

[관련 사례 006](CASEBOOK.md#case-006).

**Case013의 RTN·D16·D4**

RTN은 가중치를 가까운 허용값으로 단순 반올림하는 비교 방법입니다. D16은 공개 수식을 바탕으로 한 참조 구현의 행·열 배율을 사용하고 가중치를 INT4로 저장하며, 계산 입력은 BF16으로 유지합니다. D4는 같은 가중치를 쓰고 입력까지 INT4로 바꿉니다. 품질 계산에서는 압축 값을 BF16으로 복원합니다. D16·D4는 실험 이름이며 중간 압축·강한 가중치 압축을 뜻하지 않습니다.

[Case013](CASEBOOK.md#case-013) · [도구 작업 후속](../../research/agent_tool_contract_repair_20261014/README.ko.md).

<a id="attention"></a>
## Attention

계산한 가중치를 이용해 입력 위치들의 정보를 조합하는 연산입니다. Case 006은 질문을 처음 처리할 때 한 층의 이 연산만 바꿉니다.

[관련 사례 006](CASEBOOK.md#case-006).

<a id="mlp"></a>
## MLP와 SwiGLU

MLP는 모델 안의 순방향 계산 블록입니다. Qwen의 SwiGLU 형태에서는 up 행렬이 입력을 넓히고, gate가 어떤 중간 성분을 반영할지 조절하며, down 행렬이 출력 크기로 되돌립니다. 이런 학습된 행렬 변환을 projection이라고 합니다. Case007은 세 행렬에서 서로 대응하는 중간 성분인 채널을 함께 제거합니다.

[관련 사례 007](CASEBOOK.md#case-007).

<a id="prefill"></a>
## 질문을 처음 읽는 단계(prefill)

주어진 질문 전체를 처음 처리하는 단계입니다. 모델 prefill 시간과 그 안의 한 연산에 걸리는 시간은 측정 범위가 다릅니다.

[관련 사례 006](CASEBOOK.md#case-006).

<a id="decode"></a>
## 이후 토큰 생성(decode)

이미 주어진 토큰과 저장된 상태를 이용해 다음 토큰들을 생성하는 단계입니다. Case 006의 attention 변경은 prefill에 한정되고 decode는 BF16을 유지합니다.

[관련 사례 006](CASEBOOK.md#case-006).

**변화하는 기억: state·cache·readout**

State는 이전 입력에서 가져와 다음 입력마다 갱신하는 모델의 내부 정보입니다. Cache는 중간 정보를 다시 쓰기 위해 저장한 것입니다. Readout은 그 상태를 답변 점수로 읽는 계산입니다. Case010·011은 상태를 저장하는 방식과 답을 읽는 방식을 구분합니다. 정답 확률 점수가 좋아져도 첫 오답이 늦게 나오지는 않을 수 있습니다. Patch는 변경한 매개변수를 담은 파일로, 반드시 전체 새 모델을 뜻하지는 않습니다.

[Case010](CASEBOOK.md#case-010) · [Case011](CASEBOOK.md#case-011).

<a id="kernel"></a>
## 커널(kernel)과 전체 호출 비용

커널은 장치에서 수치 연산을 수행하는 프로그램입니다. 호출 전체에는 데이터 준비·양자화·변환도 들어갈 수 있어, 커널 시간만 재면 이 비용이 빠집니다.

[관련 사례 004](CASEBOOK.md#case-004).

<a id="latency"></a>
## 실행 시간(latency)

정해진 작업에 걸리는 시간입니다. MLP 하나, attention 호출, 질문 전체 처리, 답변 생성 중 무엇을 쟀는지 함께 읽어야 합니다. 서로 다른 범위의 속도비는 바꿔 쓸 수 없습니다.

[관련 사례 007](CASEBOOK.md#case-007).

**요청 처리: serving·graph/eager·처리량·TPOT**

Serving은 요청을 받아 모델 답변을 생성하는 일입니다. 동시 요청 수(concurrency)는 한꺼번에 진행할 수 있는 요청 수, 처리량(throughput)은 단위 시간에 완료한 작업량입니다. TPOT는 기록된 정의에 따라 첫 토큰 뒤의 출력 토큰당 평균 시간을 뜻합니다. Graph는 미리 준비한 GPU 실행 순서를 재사용하고, eager는 매번 연산을 호출합니다. 모델은 같은 실행 방식 안에서 비교하고, 시간을 잰 범위도 함께 읽습니다.

[Case009 요청 측정](CASEBOOK.md#case-009).

<a id="accuracy"></a>
## 정답률과 정답(gold)

정답률은 과제의 채점 규칙에 따라 맞힌 답의 비율입니다. Gold는 별도로 정한 정답입니다. 기준선이 맞혔지만 후보가 틀리면 회귀, 기준선이 틀렸지만 후보가 맞히면 개선으로 셉니다.

[관련 사례 006](CASEBOOK.md#case-006).

**도구 호출 규칙: schema·contract·enum·validation**

Schema는 요청·결과의 허용 필드와 값 형식입니다. Contract는 호출자와 도구가 지켜야 하는 규칙입니다. Enum은 허용값을 열거한 목록으로, Case013 후속에서는 등록한 이름으로만 도구를 호출하게 제한합니다. Validation은 특정 요구사항을 검사하는 일입니다. 이 연구는 AI의 최종 성공 메시지와 별도로 실제 파일 변경·검사 실행 기록을 확인합니다.

[도구 작업 후속](../../research/agent_tool_contract_repair_20261014/README.ko.md).

<a id="probability"></a>
## 확률(probability)

모델은 가능한 다음 토큰에 확률을 부여합니다. 네 선택지 평가에서는 그 네 라벨 안에서 확률을 다시 정규화하므로, 전체 어휘에서의 확률과 다를 수 있습니다.

[관련 사례 006](CASEBOOK.md#case-006).

<a id="nll"></a>
## 음의 로그우도(NLL)

정답이나 실제 다음 토큰에 준 확률로 계산하는 벌점이며 낮을수록 좋습니다. 후보−기준선의 NLL 변화는 양수일 때 나빠지는 방향입니다. 네 보기 실험의 선택지 NLL은 허용된 네 라벨 안의 확률을, 전체 어휘 NLL은 그 밖에 준 확률도 반영합니다. Case011의 교차 엔트로피(CE)도 정답 확률에 대한 관련 손실입니다. 이 점수들은 정답 개수를 세는 정답률과 다릅니다.

[관련 사례 007](CASEBOOK.md#case-007).

**텍스트 예측 점수: perplexity(PPL)**

글의 실제 다음 토큰에 모델이 준 확률을 요약한 점수입니다. 같은 글·채점 설정에서는 낮을수록 좋습니다. 업무 정답률은 아니며, 글이나 토큰 분리 규칙이 다르면 모델 능력을 직접 줄 세울 수 없습니다. Case014의 PG19 결과는 책 구간에 관한 것이고 ArXiv 논문에서는 같은 이득을 확인하지 못했습니다.

[Case013 문장 점수](CASEBOOK.md#case-013) · [Case014 문서 비교](CASEBOOK.md#case-014).

<a id="kl"></a>
## 분포 차이(KL divergence)

두 확률 분포를 방향을 정해 비교하는 값입니다. 여기서 KL(B ∥ candidate)는 원래 모델 B와 변경 모델을 비교합니다. 작으면 분포가 더 가깝지만, 과제 정답을 더 잘 맞힌다는 뜻은 아닙니다.

[관련 사례 007](CASEBOOK.md#case-007).

<a id="pruning"></a>
## 구조화 가지치기(pruning)

모델의 매개변수 그룹과 대응 계산을 제거하는 작업입니다. Case 007은 해당 MLP 행렬을 실제로 자릅니다. 25%·50% 제거는 그 블록의 채널 그룹 비율이며 모델 전체 비율이 아닙니다.

[관련 사례 007](CASEBOOK.md#case-007).

**작은 블록의 가중치 맞추기: ridge 회귀**

작은 블록의 출력을 목표 출력에 가깝게 맞추면서 가중치가 지나치게 커지지 않게 벌점을 주는 방법입니다. Case008 R은 이미 정한 작은 출력 행렬에 적용합니다. 제거한 채널을 되살리거나 새 기초 모델을 학습하는 작업은 아닙니다. FP64와 Cholesky는 이 적합에 쓴 계산 정밀도와 수치 풀이 방법입니다.

[Case008 R](CASEBOOK.md#case-008).

<a id="baseline"></a>
## 비교 기준선(baseline)

비교의 기준이 되는 원래 설정입니다. Case 007·006에서 B는 가지치기나 해당 연산 변경을 하지 않은 BF16 설정입니다. 그 답을 유지하는 것과 별도 정답에 맞는 것은 다릅니다.

[관련 사례 007](CASEBOOK.md#case-007).

<a id="held-out"></a>
## 선택에 쓰지 않은 평가 입력(held-out)

보정과 선택에 사용하지 않고 남겨 둔 입력입니다. Case 007은 그룹을 먼저 고른 뒤 평가 입력 192개로 확인했습니다. 공개된 기록을 나중에 다시 읽는 것은 새로운 평가가 아닙니다.

[관련 사례 007](CASEBOOK.md#case-007).

**설정용·평가용 입력: CAL·DEV·TEST**

보정 자료(calibration, CAL)는 변환이나 가중치 적합에 필요한 통계를 제공합니다. 개발 자료(development, DEV)는 설정을 조정하거나 구현을 확인할 때 쓰는 문제입니다. Held-out·TEST는 정해 둔 절차에 따라 그 결정에서 제외한 평가 입력입니다. Case013의 DEV 8문제는 이미 설정 조정에 쓰던 문제이므로 다시 풀어도 새 문제의 성능 평가가 되지 않습니다. Case014의 P0·P1·P1b·P2는 연구 단계 이름이며 난이도나 상품 등급이 아닙니다.

[Case013 확인 범위](CASEBOOK.md#case-013) · [Case014 연구 단계](CASEBOOK.md#case-014).

<a id="post-hoc"></a>
## 사후 분석(post-hoc)과 출력 계산(readout) 진단

사후 분석은 결과를 본 뒤 질문을 정해 조사한 것입니다. Readout은 마지막 모델 상태를 어휘 점수로 바꾸는 출력 계산입니다. Case 006의 FP32 추가 진단은 같은 입력과 상태를 재사용하며 원실험과 따로 표시합니다.

[관련 사례 006](CASEBOOK.md#case-006).

**기록 확인: hash·manifest·검산·신뢰구간**

Hash는 파일 변경을 찾는 지문이고, manifest는 파일·데이터와 그 식별 정보를 적은 목록입니다. 검산(audit)은 명시한 검사나 계산을 다시 하는 일로, 새 모델 실행 대신 저장된 값만 확인할 수도 있습니다. 신뢰구간(confidence interval, CI)은 정한 표집 방법에서의 불확실성을 나타냅니다. 차이의 구간에 0이 있다고 두 방법이 동등하다고 입증한 것은 아닙니다. `NOT_ASSESSED` 같은 상태는 배포 적합성 등 해당 판단을 평가하지 않았다는 뜻입니다.

[로컬 검사의 범위](GETTING_STARTED.md).

<a id="local-error"></a>
## 국소 출력 오차

[관련 사례 005](CASEBOOK.md#case-005).
