## 001 — 커널 선택 조건을 고치면 실행할 수 있는가?

<!-- claims: c001-runtime -->

[목표](#case-001-objective) · [데이터셋](#case-001-data) · [가정과 이론](#case-001-theory) · [실험 설계](#case-001-design) · [검증 내용](#case-001-validation) · [결과](#case-001-results) · [결과 해석](#case-001-interpretation) · [결론](#case-001-conclusion)

<a id="case-001-objective"></a>
### 1. 목표

RTX 5080에서 INT8 모델 실행이 막히는 원인을 찾고, 기존 upstream 선택 조건으로 해결되는지 확인했습니다. 조사 대상은 계산 속도보다 먼저 필요한 실행 호환성입니다.

<a id="case-001-data"></a>
### 2. 데이터셋

같은 RedHatAI Qwen2.5-0.5B W8A8 체크포인트와 짧은 프랑스 수도 질문을 사용했습니다. 대규모 품질 평가 데이터셋이 아니라 초기화·생성 경로를 확인하는 입력입니다.

<a id="case-001-theory"></a>
### 3. 가정과 이론

지원하지 않는 커널을 먼저 선택하면 사용 가능한 대체 구현이 있어도 실패할 수 있습니다. SM120에서 지원 여부를 검사해 Triton INT8 경로를 선택하도록 하는 기존 guard를 검증했습니다.

<a id="case-001-design"></a>
### 4. 실험 설계

공식 vLLM 0.29.0 wheel에 hclsys의 PR 중 Python runtime guard만 적용했습니다. 같은 PC·환경·모델에서 수정 전후를 비교했습니다. guard와 Triton 커널 자체는 upstream의 구현입니다.

<a id="case-001-validation"></a>
### 5. 검증 내용

프로세스 종료 코드, 생성 결과, CUDA 가중치 dtype과 로드된 모듈의 선택 경로를 확인했습니다. 환경 잠금 자료와 실행 증거를 남겨 같은 조건을 추적할 수 있게 했습니다.

<a id="case-001-results"></a>
### 6. 결과

수정 전 초기화는 exit 1로 실패했습니다. 수정 후 생성은 exit 0으로 끝났고 “The capital of France is Paris.”를 출력했습니다. INT8 모듈 96개가 `TritonInt8ScaledMMLinearKernel`을 선택했습니다.

<a id="case-001-interpretation"></a>
### 7. 결과 해석

96은 로드된 모듈 수이며 GPU 커널 동적 호출 96회가 아닙니다. 한 질문의 성공으로 처리량·일반 과제 품질이나 PR 전체 빌드를 검증한 것은 아닙니다.

<a id="case-001-conclusion"></a>
### 8. 결론

해당 환경의 실행 호환성 문제를 기존 guard로 해소하는 경로를 확인했습니다. 프로젝트가 만든 것은 수정 전후 재현 도구와 실행 증거이며, 새 INT8 커널이 아닙니다.

## 002 — 공식 FP8 체크포인트로 바꾸면 무엇이 달라지는가?

<!-- claims: c002-quality c002-cost -->

[목표](#case-002-objective) · [데이터셋](#case-002-data) · [가정과 이론](#case-002-theory) · [실험 설계](#case-002-design) · [검증 내용](#case-002-validation) · [결과](#case-002-results) · [결과 해석](#case-002-interpretation) · [결론](#case-002-conclusion)

<a id="case-002-objective"></a>
### 1. 목표

공식 FP8 모델로 바꿀 때 한국어 문서 추출 결과와 메모리·요청 시간이 어떻게 달라지는지 비교했습니다.

<a id="case-002-data"></a>
### 2. 데이터셋

한국어 합성 문서 100개에 담당자·작업·날짜·금액을 넣고 확정 변경까지 반영한 정답을 먼저 만들었습니다. 같은 100개를 세 라운드 반복했으며 독립 문서 300개로 세지 않습니다.

<a id="case-002-theory"></a>
### 3. 가정과 이론

JSON 문법을 지키는 것과 네 필드를 모두 맞히는 것은 다른 조건입니다. 더 작은 가중치 형식의 자원 이득과 과제 정답을 함께 봐야 모델 교체를 판단할 수 있습니다.

<a id="case-002-design"></a>
### 4. 실험 설계

공식 Qwen3-4B-Instruct-2507 BF16·FP8 체크포인트를 같은 과제로 비교했습니다. KV cache는 동일한 1 GiB BF16 예산으로 고정하고 streaming client로 요청을 기록했습니다.

<a id="case-002-validation"></a>
### 5. 검증 내용

네 필드가 모두 맞아야 문서 정답으로 채점했습니다. 같은 문서의 두 출력을 대응시켜 정답률 차이와 구간을 계산하고, 요청 시간과 장치 전체 메모리를 기록했습니다.

<a id="case-002-results"></a>
### 6. 결과

첫 품질 평가에서 BF16은 31/100, FP8은 32/100이었습니다. FP8−BF16 차이는 +1 퍼센트포인트(%p), 95% 구간은 −2~+5%p였습니다. 관측 최대 메모리는 약 11.62 GiB와 8.21 GiB였습니다.

<a id="case-002-interpretation"></a>
### 7. 결과 해석

FP8 요청은 대체로 먼저 끝났지만 출력 길이가 달라 순수 decode 속도 비교는 아닙니다. 장치 메모리에는 배경 할당도 포함됩니다. JSON이 맞아도 두 모델의 추출 정답률은 낮았습니다.

<a id="case-002-conclusion"></a>
### 8. 결론

공식 체크포인트를 바꿨을 때의 자원 사용과 추출 성능을 같은 입력에서 확인했습니다. 정답 한 개 차이는 개선이나 동등성의 확증이 아니며, 새 quantizer나 완성된 추출 서비스를 만든 실험이 아닙니다.

## 003 — 수치 비교의 기준이 달라지면 결론은 어떻게 달라지는가?

<!-- claims: c003-reference -->

[목표](#case-003-objective) · [데이터셋](#case-003-data) · [가정과 이론](#case-003-theory) · [실험 설계](#case-003-design) · [검증 내용](#case-003-validation) · [결과](#case-003-results) · [결과 해석](#case-003-interpretation) · [결론](#case-003-conclusion)

<a id="case-003-objective"></a>
### 1. 목표

EFQ-Softmax 수치 근사의 오차를 독립 구현으로 확인하고, 코드 매핑의 효과와 비교 기준의 scale 선택을 나누어 조사했습니다.

<a id="case-003-data"></a>
### 2. 데이터셋

실제 Qwen3-0.6B에서 얻은 attention trace를 사용했습니다. 길이 512·2048·4096 각각에서 16문서×3층×4heads의 192개 head 단위를 비교했습니다. 문서 안의 head는 독립 표본이 아닙니다.

<a id="case-003-theory"></a>
### 3. 가정과 이론

같은 scale의 기준과 비슷한 근사라도 다른 scale 규칙의 기준보다 오차가 클 수 있습니다. 같은-scale 비교는 코드 매핑을, headroom 기준 비교는 비교 대상의 scale 선택까지 포함합니다.

<a id="case-003-design"></a>
### 4. 실험 설계

논문 식을 독립 구현하고 Q/K/V·mask·FP32 계산 조건을 공통으로 유지했습니다. 개발 자료로 선택한 EFQ 설정, EFQ scale의 nearest rounding, 별도 headroom scale의 nearest를 구분했습니다.

<a id="case-003-validation"></a>
### 5. 검증 내용

식·구현 검사와 trace 수집 검증을 수행하고 보존한 증거로 수치 분해를 재계산했습니다. 원래 screen은 같은-scale nearest를 기준으로 하며 headroom 기준으로 사후 교체하지 않았습니다.

<a id="case-003-results"></a>
### 6. 결과

EFQ-Mean 상대 출력 오차 중앙값은 세 길이에서 11.49~14.49%였습니다. 개발 자료의 선택은 EFQ-MMLU와 같았고 같은-scale nearest와 집계상 비슷했습니다. 그러나 보정 EFQ의 중앙값 오차는 headroom nearest 대비 1.133×·1.179×·1.148×였습니다.

<a id="case-003-interpretation"></a>
### 7. 결과 해석

headroom nearest는 모든 길이에서 중앙값과 p95가 더 낮았습니다. 같은-scale 기준에서의 결과와 더 낮은 오차를 내는 다른 기준의 결과를 분리해야 합니다.

<a id="case-003-conclusion"></a>
### 8. 결론

프로젝트는 Han과 공동저자의 EFQ 방법을 식에서 구현하고 비교 기준에 따른 해석을 검증했습니다. FP32 수치 모사이므로 packed-FP4 하드웨어 실행·속도나 downstream 품질 결과는 아닙니다.

## 004 — attention 연산 전체를 호출해도 빠른가?

<!-- claims: c004-cost -->

[목표](#case-004-objective) · [데이터셋](#case-004-data) · [가정과 이론](#case-004-theory) · [실험 설계](#case-004-design) · [검증 내용](#case-004-validation) · [결과](#case-004-results) · [결과 해석](#case-004-interpretation) · [결론](#case-004-conclusion)

<a id="case-004-objective"></a>
### 1. 목표

저정밀 attention이 커널 내부뿐 아니라 전처리·변환을 포함한 전체 호출에서도 빠른지, 국소 오차와 함께 확인했습니다.

<a id="case-004-data"></a>
### 2. 데이터셋

Qwen3-0.6B layer 13에서 얻은 16개 문서 입력을 길이 512·2048·4096에서 평가했습니다. 실제 Qwen H16/H8 geometry와 별도 합성 H8/H8 조건은 다른 비교입니다.

<a id="case-004-theory"></a>
### 3. 가정과 이론

BF16 Q/K/V를 저정밀 연산에 맞게 준비하는 시간도 호출 비용입니다. 길이가 짧으면 준비 비용이 커널의 이득을 넘을 수 있습니다. 국소 출력 오차는 과제 정답률과 다른 지표입니다.

<a id="case-004-design"></a>
### 4. 실험 설계

공식 SageAttention INT8-QK/FP8-PV와 개발 자료에서 선택하고 fused 실행을 확인한 BF16 SDPA를 비교했습니다. GPU의 BF16 입력부터 BF16 출력까지 smoothing·양자화·변환·wrapper를 포함했습니다.

<a id="case-004-validation"></a>
### 5. 검증 내용

실제 실행 경로와 유효성을 검사하고 쌍별 비용을 측정했습니다. 호출은 모든 query를 처리하며, 오차는 head별 고정 query 32개와 각 위치에서 허용되는 모든 key를 사용했습니다.

<a id="case-004-results"></a>
### 6. 결과

길이 512·2048·4096의 전체 연산 속도비는 0.373×·1.465×·2.100×였습니다. 세 실제 Qwen 조건 모두 고정 국소 오차 기준인 중앙값 ≤1%, p95 ≤3%를 넘었습니다.

<a id="case-004-interpretation"></a>
### 7. 결과 해석

속도비가 1보다 작으면 느리다는 뜻입니다. 긴 호출의 속도 이득과 오차 기준 탈락이 함께 관측됐습니다. head·길이 반복은 독립 문서를 늘리지 않으며 이 시간은 모델 전체 시간이 아닙니다.

<a id="case-004-conclusion"></a>
### 8. 결론

측정 경계에 따라 속도 판단이 달라진다는 점을 실제 입력에서 확인했습니다. 어댑터·경로 검사·전체 호출 측정은 프로젝트의 작업이고, 커널은 SageAttention의 구현입니다.

## 005 — 설정을 바꾸면 오차와 비용의 절충이 나아지는가?

<!-- claims: c005-stop c005-tradeoff c005-validity -->

[목표](#case-005-objective) · [데이터셋](#case-005-data) · [가정과 이론](#case-005-theory) · [실험 설계](#case-005-design) · [검증 내용](#case-005-validation) · [결과](#case-005-results) · [결과 해석](#case-005-interpretation) · [결론](#case-005-conclusion)

<a id="case-005-objective"></a>
### 1. 목표

Case004의 attention 경로 주변에서 정밀도 설정을 제한적으로 바꾸어 국소 오차를 낮추면서 전체 호출 속도를 유지할 수 있는지 조사했습니다.

<a id="case-005-data"></a>
### 2. 데이터셋

개발 입력은 합성 문서 8개를 사용한 Qwen3-0.6B layer 13, causal L4096입니다. 개발에서 중단했으므로 새로운 확인 집합의 결과는 없습니다.

<a id="case-005-theory"></a>
### 3. 가정과 이론

정밀도를 바꾸면 오차뿐 아니라 변환·누산·scale 처리 비용도 달라집니다. 중앙값 오차 ≤1%, p95 ≤3%, 유효한 전체 출력, 속도비 ≥1.50×를 함께 충족해야 다음 단계로 진행하는 고정 규칙을 사용했습니다.

<a id="case-005-design"></a>
### 4. 실험 설계

기준 A_PUBLIC 주변의 변경 설정 V1–V4를 명시적 진입점으로 비교했습니다. top-level 옵션이 실제 dispatch에 반영되는지 감사하고 작은 유효성 검사 뒤 실제 개발 입력을 실행했습니다.

<a id="case-005-validation"></a>
### 5. 검증 내용

NaN/Inf 등 출력 유효성, sampled-query 오차와 전체 호출 시간을 확인했습니다. V3는 작은 fixture에서 중심화된 V 범위가 0이 되는 경로로 NaN/Inf가 포함된 유효하지 않은 출력을 내어 제외됐습니다.

<a id="case-005-results"></a>
### 6. 결과

유효한 변경 설정 세 개 중 모든 기준을 충족한 설정은 없었습니다. V4의 중앙값 오차는 A_PUBLIC의 2.294%에서 1.958%로 낮아졌고, 속도비는 2.110×에서 1.338×로 낮아졌습니다. 판정은 **STOP_DEV_SCREEN**입니다.

<a id="case-005-interpretation"></a>
### 7. 결과 해석

V4는 충실도와 비용의 절충점입니다. V1/V2는 속도를 유지했지만 집계 오차 감소가 작았으며 누산과 V 범위 정책이 함께 바뀌어 원인분해가 아닙니다. V3 실패는 버전을 고정한 특정 구현 경계의 관측입니다.

<a id="case-005-conclusion"></a>
### 8. 결론

최종 후보 없이 개발 screen에서 완료·중단했습니다. 사후 임계값 민감도는 해석 자료로 남으며 원래 기준을 완화한 새 통과 결과가 아닙니다. 국소 오차로 저정밀 attention 전체나 모델 과제 품질을 판정하지 않습니다.

<a id="case-006"></a>
## 006 — 점수와 개별 답변 선택은 언제 달라지는가?

<!-- claims: c006-native c006-readout c006-limits c006-timing c006-implementation -->

[목표](#case-006-objective) · [데이터셋](#case-006-data) · [가정과 이론](#case-006-theory) · [실험 설계](#case-006-design) · [검증 내용](#case-006-validation) · [결과](#case-006-results) · [결과 해석](#case-006-interpretation) · [결론](#case-006-conclusion)

<a id="case-006-objective"></a>
### 1. 목표

정답 수가 비슷하더라도 같은 문제를 맞힌 것인지, 정답에 준 확률까지 비슷한지 알고 싶었습니다. 같은 모델·질문에서 attention 계산 경로만 바꾸어 출력 차이를 추적했습니다.

B는 원래 모델의 BF16 계산을 그대로 쓰는 비교 기준입니다. A_PUBLIC과 V4는 다른 모델의 이름이 아니라, 한 attention 연산을 계산하는 설정 이름입니다. A_PUBLIC은 앞선 Case 005에서도 사용한 공개 기준 설정이고, V4는 그 사례의 네 번째 변경 설정에서 이어온 이름입니다. V4는 FP4나 4비트 정밀도를 뜻하지 않습니다.

BF16과 FP16은 서로 다른 16비트 부동소수점 형식, FP8은 8비트 부동소수점 형식, INT8은 8비트 정수 형식입니다. 표현 가능한 수와 간격이 달라 계산 결과·변환 비용도 달라질 수 있습니다. 이 사례에서는 모델 가중치를 BF16으로 유지하고, 아래 attention 곱셈 경로를 바꿨습니다.

**설정별로 무엇을 바꿨나?**

**원래 계산 · B**

- 참조할 위치의 점수 · QK 곱: BF16 SDPA 경로
- 정보를 섞는 출력 · PV 곱: BF16 SDPA 경로

**FP8 값 결합 경로 · A_PUBLIC**

- 참조할 위치의 점수 · QK 곱: Q·K를 INT8로 표현하는 경로
- 정보를 섞는 출력 · PV 곱: FP8 PV; 기록된 누산 옵션 fp32+fp16

**FP16 값 결합 경로 · V4**

- 참조할 위치의 점수 · QK 곱: Q·K를 INT8로 표현하는 경로
- 정보를 섞는 출력 · PV 곱: FP16 PV; 기록된 누산 옵션 fp32

누산은 곱한 값들을 더하는 과정입니다. 숫자 형식은 각 경로의 피연산자 형식을 뜻하며, 모든 중간 계산이 같은 비트 수로 실행된다는 뜻은 아닙니다. 두 저정밀 경로의 최종 attention 출력은 모두 BF16입니다.

[방법·계산 근거 — 영어](../../cases/006-attention-decision-stability/METHODS.md)

<a id="case-006-data"></a>
### 2. 데이터셋

영어 합성 4지선다 과제입니다. RETRIEVAL은 사실 찾기, COMPARISON은 사실의 비교·관계 판단, CODE는 제한된 짧은 프로그램의 결과 예측입니다. 모델을 심사자로 쓰지 않고 정답을 먼저 계산했습니다.

본 평가 입력은 모두 4,096토큰이며 불필요한 채움 부분만 조정했습니다. 표준 평가를 B의 정답 여부나 점수로 걸러내지 않았습니다. 스트레스 집합은 별도 풀에서 B의 최고점 간격을 이용해 선정했으므로 두 집합의 비율을 합치지 않습니다.

자료 | 입력 수 | 용도
--- | --- | ---
개발 / 별도 smoke | 96 / 6 | 표현·개입·단일 토큰 답안 검사
표준 평가 · standard | 192 (과제별 64) | 필터링하지 않은 본 비교

<a id="case-006-theory"></a>
### 3. 가정과 이론

Attention을 두 단계로 읽으면 QK와 PV가 무엇인지 알 수 있습니다. Q(query)는 현재 위치에서 찾을 정보를, K(key)는 각 위치와의 관련성을 비교하는 데 쓰는 수치 벡터이고, V(value)는 결합할 내용의 벡터입니다. 이 명칭은 모델 내부의 학습된 수치 표현을 가리킵니다.

① QK 곱: 현재 위치의 Q와 각 허용 위치의 K를 내적해 참조 점수를 만듭니다. 미래 위치를 가리는 causal mask와 점수의 정규화를 거쳐 가중치 P를 만듭니다. Softmax는 이 점수들을 합이 1인 가중치로 바꾸는 함수입니다.

② PV 곱: 가중치 P에 따라 각 위치의 V를 곱해 더하여 attention 출력을 만듭니다. A_PUBLIC과 V4는 둘 다 QK에 INT8 경로를 쓰고, 이 값 결합 단계에서 FP8과 FP16 경로로 갈립니다.

실행은 각각 SageAttention의 명시적 FP8-PV / FP16-PV 함수로 연결했습니다. 같은 K 중심화(smooth_k=True), V 중심화 없음(smooth_v=False), per_warp Q/K 양자화 묶음을 사용했습니다. A_PUBLIC의 기록된 V scale 최대값은 2.25이며, V4의 필요한 BF16→FP16 V 변환은 호출 안에 포함됩니다. Scale은 값을 저정밀 표현 범위에 맞추는 배율입니다.

곱셈 형식뿐 아니라 누산·scale·변환 경로가 묶여 바뀝니다. 따라서 두 설정의 차이를 FP8 대 FP16 한 요소의 원인 효과로만 단정할 수 없습니다. 숫자 표현을 바꾸면서 생긴 국소 출력 차이가 최종 답변에 얼마나 이어지는지는 나머지 모델 계산에 달려 있습니다.

NLL은 정답 선택지 확률의 음의 로그로 낮을수록 좋습니다. ΔNLL=후보−B이므로 양수는 더 나쁜 방향입니다. 선택 변경은 B와 다른 답을 고른 경우이며, 회귀는 B의 정답을 후보가 잃은 경우입니다. B의 오답을 맞히는 정답 획득이나 다른 오답으로의 변경도 따로 셉니다.

최고점 동률은 저장된 선택지 점수가 정확히 같은 상태입니다. 표시용 반올림이나 임의의 작은 허용값으로 정의하지 않고 원래의 결정적 동률 해소 규칙을 유지했습니다.

[방법·계산 근거 — 영어](../../cases/006-attention-decision-stability/METHODS.md)

<a id="case-006-design"></a>
### 4. 실험 설계

Qwen3-0.6B의 0부터 센 layer 13에서 관측한 프롬프트를 한 번 처리하는 prefill attention만 교체했습니다. 다른 층과 이후 decode는 BF16입니다. 모든 설정이 같은 토큰·가중치·마스크를 사용하고 미래 정답 토큰은 입력에 넣지 않았습니다.

사후 readout 진단은 같은 표준 192개와 선정 스트레스 46개를 재사용했습니다. 각 설정의 같은 최종 hidden state와 BF16에 표현된 가중치를 FP32로 계산한 출력 head를 따로 평가했습니다. 후보와 B는 항상 같은 readout 안에서 비교합니다. 새로운 독립 평가나 모델 개선 설정이 아닙니다.

[방법·계산 근거 — 영어](../../cases/006-attention-decision-stability/METHODS.md)

<a id="case-006-validation"></a>
### 5. 검증 내용

교체하지 않은 모델과 B 경로의 일치, layer 13만 호출되는지, 동일 Q/K/V, 입력 비변조와 예외 시 복구를 확인했습니다. 네 선택지만이 아니라 attention·모든 decoder block·최종 norm·전체 어휘 출력의 유효성을 검사했습니다.

정답 선택지는 실제 이어쓰기 문맥에서 각각 한 토큰인지 확인했습니다. 과제별 가중치를 같게 둔 쌍별 NLL 변화에 대해 입력 단위 5,000회 재표집으로 95% 구간을 계산했습니다.

사후 진단에서는 원래 출력을 단순히 넓은 dtype으로 바꾸는 검사, FP32 출력을 원래 dtype으로 되돌리는 검사, CPU FP64 네 선택지 내적 검사를 수행했습니다. 공개 네 선택지 기록의 재계산과 제외된 전체 벡터를 이용한 검사는 범위가 다릅니다.

<a id="case-006-results"></a>
### 6. 결과

표준 192개의 B/A_PUBLIC/V4 정답 수는 104/106/108입니다. A_PUBLIC은 192개 중 5개가 바뀌어 정답 획득 2개·다른 오답 변경 3개, V4는 192개 중 8개가 바뀌어 정답 획득 4개·다른 오답 변경 4개였습니다. 표준셋의 정답 손실은 두 설정 모두 0개였습니다. 별도 스트레스 46개에서는 A_PUBLIC 2개, V4 1개가 정답을 잃었습니다.

과제별 동일 가중치의 정답 선택지 NLL 쌍별 변화는 후보−BF16이며 양수가 더 나쁜 방향입니다. 두 설정의 평균 변화 95% 구간은 0을 포함했습니다. 원래 모델 전체 prefill 속도비는 A_PUBLIC 1.0041×, V4 1.0014×입니다.

**사후 readout 진단:** 같은 192 + 46 시나리오를 재사용했습니다. FP32 출력에서는 후보마다 표준 192개 중 3개 선택이 B와 달랐습니다. 기존 변경의 소멸과 새 변경을 함께 관측했으며, 원래 실험을 대체하지 않습니다.

<a id="case-006-interpretation"></a>
### 7. 결과 해석

원래 표준 평가의 모든 선택 변경에는 B 또는 후보의 정확한 최고점 동률이 관련됐습니다. 동률 처리는 원래 모델 동작의 일부입니다. 사후 FP32 출력에서 기존 변경 일부는 사라지고 새 변경도 생겼으므로, 이를 단순한 오류 제거로 해석할 수 없습니다.

원래 표준 평가에서 정답 손실이 0이었다는 관측은 일반적인 품질 보존을 뜻하지 않습니다. 별도 스트레스에서는 손실이 있었고, 표준 NLL 변화 구간도 동등성을 입증하는 검정이 아닙니다. B의 코드 정답은 15/64, 엄격한 구조화 생성은 모든 설정에서 0/24였습니다.

사후 출력은 같은 hidden state를 다른 산술 경로로 읽은 민감도 검사입니다. 마지막 반올림만이 모든 차이의 원인이라고 분리해 입증한 것은 아닙니다.

<a id="case-006-conclusion"></a>
### 8. 결론

한 층의 수치 개입을 정답 확률·개별 선택·동률·비용까지 추적하는 비교를 완료했습니다. 선택이 바뀌는 경우와 정답을 잃거나 얻는 경우를 구분할 수 있으며, 출력 계산 방식에 따른 민감도도 관측했습니다.

본실험 상태는 COMPLETED_CONTROLLED_STUDY, 사후 진단은 POST_HOC_SAME_INPUT_READOUT_DIAGNOSTIC, 배포 판단은 NOT_ASSESSED입니다. 합성 과제와 한 층 prefill의 결과이며 모델 전체 저정밀화나 실제 서비스 품질 판정으로 확대하지 않습니다.

<a id="case-007"></a>
## 007 — 함께 지울 그룹을 고려하면 더 나은 작은 MLP를 고를 수 있는가?

<!-- claims: c007-transfer c007-quality c007-random -->

[목표](#case-007-objective) · [데이터셋](#case-007-data) · [가정과 이론](#case-007-theory) · [실험 설계](#case-007-design) · [검증 내용](#case-007-validation) · [결과](#case-007-results) · [결과 해석](#case-007-interpretation) · [결론](#case-007-conclusion)

<a id="case-007-objective"></a>
### 1. 목표

원래 출력에 주는 변화가 작도록 MLP의 일부를 제거하고 싶었습니다. 삭제할 묶음을 하나씩 평가하는 방법과, 여러 묶음을 함께 평가하는 방법을 비교했습니다.

채널은 MLP가 토큰 하나를 처리할 때 만드는 중간값 벡터의 한 좌표입니다. 이 MLP는 입력의 1,024개 수로부터 3,072개 중간값을 계산하고, 다시 1,024개 수의 출력으로 결합합니다. 채널은 입력 문서나 단어 한 개를 뜻하지 않습니다.

그룹은 삭제 단위를 정하기 위해 이 채널들을 번호순으로 192개씩 묶은 것입니다. 그룹 0은 채널 0–191, 그룹 1은 192–383이며 그룹 15까지 있습니다. 비슷한 의미의 채널을 학습해서 모은 묶음이 아닙니다. “개별 그룹”은 이 16개 묶음 중 하나입니다.

B는 삭제 전 BF16 모델입니다. 그룹을 지우면 그 그룹에 해당하는 gate/up 행과 down 열을 함께 제거합니다. 4그룹을 지우면 768채널이 없어져 2,304채널이 남습니다. 모델 전체의 25%를 지운다는 뜻은 아닙니다.

**두 방법은 무엇을 고르는가?**

**개별 점수 선택 · INDEPENDENT**

- 계산 방법: 한 그룹만 지웠을 때 생기는 출력 변화의 제곱 크기를 보정 입력에서 평균해 점수를 만듭니다.
- 삭제 조합 선택: 점수가 작은 4개 또는 8개 그룹을 고릅니다. 그룹 사이의 상쇄·강화는 선택 점수에 넣지 않습니다.

**상호작용 포함 선택 · PAIRWISE**

- 계산 방법: 개별 점수에 더해, 두 그룹의 출력 변화가 서로 상쇄·강화되는 정도를 모든 그룹 쌍에서 계산합니다.
- 삭제 조합 선택: 지울 4개 또는 8개의 전체 조합을 평가해, 함께 삭제했을 때의 예상 제곱 오차가 가장 작은 조합을 고릅니다.

INDEPENDENT는 그룹들이 통계적으로 독립임을 증명했다는 뜻이 아닙니다. PAIRWISE의 pair는 오차 계산에 쓰는 그룹 쌍이며, 두 그룹만 지운다는 뜻이 아닙니다. 두 방법 모두 같은 96개 보정 입력을 사용했습니다.

<a id="case-007-data"></a>
### 2. 데이터셋

영어 합성 과제 세 종류를 사용했습니다. RETRIEVAL은 문맥의 키에 해당하는 사실 찾기, COMPARISON은 값 비교·계산, CODE는 제한된 짧은 코드의 결과 예측입니다. 정답(gold)은 모델이 답하기 전에 생성 규칙과 정확한 계산으로 정했습니다.

모든 입력은 질문·정답 근거를 유지한 512토큰입니다. 국소 오차는 입력당 고정 위치 32개에서 측정했습니다. 이 위치들과 여러 설정의 반복은 독립 입력 수를 늘리지 않습니다.

자료 | 입력 수 | 용도
--- | --- | ---
보정 · CALIBRATION | 96 (과제별 32) | 삭제 조합 선택
개발 · DEVELOPMENT | 48 (과제별 16) | 구현·수치 일치 검사
미관측 평가 · HELD_OUT | 192 (과제별 64) | 선택을 고정한 뒤 최종 비교
별도 smoke | 6 | 기본 실행 확인

<a id="case-007-theory"></a>
### 3. 가정과 이론

상쇄는 왜 중요할까요? 어떤 출력 방향에 한 그룹은 +3, 다른 그룹은 −3을 더한다고 가정하면 두 기여의 합은 0입니다. 둘을 함께 지워도 그 방향의 출력은 그대로입니다. 반대로 두 그룹이 각각 +3을 더한다면, 둘을 함께 지울 때 출력 변화의 크기는 6입니다.

아래 숫자는 원리를 설명하는 가상의 1차원 예시이며 실험 측정값이 아닙니다. 실제 실험에서는 각 그룹의 1,024차원 출력 기여를 보정 입력의 고정 토큰 위치들에서 계산했습니다. 그룹 기여를 계산할 때는 BF16에 표현된 입력·가중치를 FP32로 계산했습니다. 선택을 마친 실제 축소 모델은 BF16으로 평가했습니다.

이를 벡터로 쓰면 한 그룹의 출력 기여가 cᵢ이고, 여러 그룹을 지운 변화는 그 합입니다. 합의 제곱 크기는 각 기여의 제곱 크기에 모든 쌍의 부호 있는 내적 두 배를 더한 값입니다. INDEPENDENT는 앞부분만, PAIRWISE는 두 부분을 모두 사용합니다.

Q는 개별 크기와 내적을 담은 16×16 행렬입니다. 지울 그룹을 1로 표시한 벡터 z에 대해 PAIRWISE 목적값은 zᵀQz입니다. 이것은 같은 MLP 입력에서의 출력 변화에 관한 식이며, 정답 확률이나 모델 전체 품질을 직접 최적화하는 식은 아닙니다.

**설명용 예시 · 실험 측정값 아님**

가정한 출력 기여 | 개별 점수 합 | 함께 지운 변화의 제곱
--- | --- | ---
+3, −3 | 3² + (−3)² = 18 | (3 − 3)² = 0
+3, +3 | 3² + 3² = 18 | (3 + 3)² = 36

개별 점수 합은 같아도 실제 합의 크기는 다를 수 있습니다. 이 예시는 PAIRWISE가 실제 데이터에서 항상 더 좋다는 증거가 아닙니다.

<a id="case-007-design"></a>
### 4. 실험 설계

Qwen3-0.6B의 0부터 센 layer 13만 바꿨습니다. 원래 중간 폭 3,072를 연속된 192채널씩 16그룹으로 나누고, 4그룹(25%) 또는 8그룹(50%)을 지웠습니다. 다른 층과 attention은 원래 BF16 경로이며 재학습하지 않았습니다.

보정 통계로 각 예산의 모든 조합(1,820개 / 12,870개)을 계산한 뒤 선택을 고정했습니다. gate/up 행과 down 열을 실제로 잘라 폭 2,304 / 1,536의 작은 행렬을 만들었습니다. 0으로 가린 큰 행렬은 일치 검사용 기준으로만 사용했습니다.

미리 고정한 무작위 삭제 집합 20개/예산도 같은 입력의 국소 오차로 비교했습니다. 무작위 모델의 답변 품질·전체 시간은 측정하지 않았습니다.

<a id="case-007-validation"></a>
### 5. 검증 내용

개발 단계에서 그룹 합과 직접 삭제 오차의 일치, 행·열 인덱스 대응, 실제 축소와 가림 계산의 수치 일치, 예외 발생 후 원래 모듈 복구를 검사했습니다. 평가에서는 전체 모델 출력의 NaN/Inf와 입력·선택 식별자를 확인했습니다.

불확실성은 입력을 단위로 과제 안에서 쌍을 유지해 5,000회 재표집한 95% 구간입니다. 국소 오차, 정답 선택지 확률, 전체 어휘 분포 차이와 시간을 따로 측정했습니다. 공개 스칼라 검산은 저장된 값을 재계산하며, 제외된 전체 hidden/logit 벡터나 GPU 연산을 복원하지 않습니다.

<a id="case-007-results"></a>
### 6. 결과

25%의 평균 국소 상대오차는 INDEPENDENT 29.8291%, PAIRWISE 29.6288%였습니다. PAIRWISE−INDEPENDENT 쌍별 차이는 −0.200277퍼센트포인트, 95% 구간 [−0.284779, −0.114472]이며, 141/192개에서 오차가 낮았습니다. 50%에서는 삭제 집합·가중치·출력이 같았습니다. 두 선택법 모두 고정 무작위 집합 20개/예산 각각보다 평균 국소 오차가 낮았습니다.

25%에서 선택 변경은 INDEPENDENT 48/192, PAIRWISE 12/192였고 PAIRWISE의 전체 어휘 KL(B ∥ 후보)가 낮았습니다. 그러나 사후 직접 비교의 PAIRWISE−INDEPENDENT 정답 NLL은 +0.069860 nats, 95% 구간 [0.025925, 0.111997]로 PAIRWISE가 더 나빴습니다. 국소 MLP 속도비는 1.176–1.412×였고 모델 전체 prefill 속도비 구간은 모두 1을 포함했습니다.

<a id="case-007-interpretation"></a>
### 7. 결과 해석

25%에서는 PAIRWISE가 국소 오차를 소폭 낮추고 B의 어휘 분포·선택에 더 가까웠습니다. 그러나 별도로 계산한 정답의 확률 손실인 NLL은 INDEPENDENT가 더 좋았습니다. B에 가까운 계산과 더 좋은 정답 점수는 다른 목표입니다.

50%는 두 방법이 같은 그룹·가중치·출력을 만든 비교입니다. 차이의 [0, 0] 구간을 독립적인 품질 동등성 증거로 읽을 수 없습니다. 무작위 집합 결과는 고정한 20개에 대한 기술통계이며 전체 조합의 최적성을 뜻하지 않습니다.

B의 과제별 정답은 사실 찾기 63/64, 비교 15/64, 코드 16/64였습니다. 이 낮은 기준 성능과 합성 선택형 과제 범위 안에서 답변 변화를 해석해야 합니다.

<a id="case-007-conclusion"></a>
### 8. 결론

삭제 조합 선택 → 실제 행렬 축소 → 미관측 입력 → 답변 점수와 비용을 연결한 비교를 완료했습니다. 25%에서 작은 국소 개선을 관측했고 50%에서는 동일한 구조를 얻었습니다.

원래 규칙은 두 예산 모두에서 PAIRWISE−INDEPENDENT 국소 오차 차이의 95% 구간 상한이 0보다 작아야 긍정적 전이라고 판정합니다. 종합 결과는 COMPLETED_NO_CLEAR_TRANSFER, 배포 적합성은 NOT_ASSESSED입니다. 한 모델·한 층·재학습 없는 실험의 결론입니다.

## 여기서 사용하는 용어

- **추론(inference):** 이미 학습된 모델을 실행해 점수나 출력을 얻는 과정입니다.
- **양자화·BF16/FP8/INT8:** 제한된 정밀도의 수 표현을 사용합니다. 가중치와 attention의 각 피연산자가 같은 형식일 필요는 없습니다.
- **Attention:** query와 key로 구한 점수를 이용해 value 벡터를 결합하는 연산입니다.
- **Prefill / decode:** 관측한 프롬프트를 처리하는 단계 / cache를 사용해 이후 토큰을 생성하는 단계입니다.
- **전체 연산 비용:** 필요한 준비와 출력 변환까지 포함한 측정 대상 어댑터의 호출 비용입니다.
- **국소 출력 오차:** 한 연산 경계의 수치 차이이며 과제 정답률 손실과 다릅니다.
- **Gold:** BF16 모델 예측이 아닌, 별도로 확정한 정답입니다.
- **쌍별 비교:** 같은 입력을 설정이나 반복 간에 대응시킨 뒤 차이를 계산합니다.
- **최고점 동률:** 기록된 계산에서 허용 선택지의 최대 점수가 정확히 같은 경우입니다.
- **사후 진단:** 결과를 본 뒤 동기가 생긴 분석으로, 원래 고정 평가와 구분합니다.
- **Readout:** 최종 hidden state를 어휘 점수로 바꾸는 출력 projection입니다.
