Qwen3-4B-Instruct-2507 실전 안내

작게 저장한 모델이 다시 실행되는지, 빨라지는지, 업무까지 수행하는지 따로 확인했습니다.

아래는 RTX 5080 16GB의 기존 기록을 연결한 안내입니다. BF16은 원래 16비트 가중치를 쓰는 비교 기준선이며, W4A16은 가중치 4비트·활성값 16비트를 뜻합니다. 활성값은 실행 중 계산되는 숫자입니다.

한눈에 보는 결론판단 범위모델·환경실행·재확인결과문제·완화구현·출처원자료·이력

2. 이 자료로 판단할 수 있는 것

같은 장치에서 실제 실행된 저장 형식, 압축 파일의 검사·재로딩 절차, 같은 요청 조건의 비용 차이, 관측된 답변·도구 실패를 확인할 수 있습니다. 모델 변경 전에 어떤 항목을 다시 측정할지도 정할 수 있습니다.

다른 16GB GPU의 호환성, 모든 INT4나 DualQuant의 품질, 자신의 업무 정확도, 최대 안정 문맥 길이, 상용 운영 안정성은 판단할 수 없습니다. 개발과 실패 관찰에 사용한 작은 과제 집합(DEV)의 회복은 별도 입력의 검증을 대신하지 않습니다.

5. 품질·속도·메모리 결과

측정 방법과 결과 읽는 법을 공통 기준으로 사용합니다. 아래 표끼리는 서로 다른 실험 조건이므로 하나의 성능 점수로 합산하지 않습니다.

가중치 파일과 실행 중 메모리 — Case008 Q

{{storage_table}}

GB는 10⁹ B, GiB는 2³⁰ B입니다. 가중치 파일은 {{file_reduction}} 감소했습니다. Torch allocator peak는 초기화·캐시·실행을 포함한 별도 측정이며 장치 전체 사용량은 아닙니다. 저장·새 프로세스 실행은 확인했지만 짧은 eager 요청의 속도 우위는 확인하지 못했습니다.

{{source_bf16_files}} · {{source_storage}} · 원래 192개 합성 평가 입력의 품질·8토큰 시간 결과

조건별 출력 처리량 — Case009

CUDA graph는 반복되는 GPU 작업의 실행 준비 비용을 줄이는 방식입니다. Eager는 작업을 그때그때 실행하는 대조 조건입니다. 각 방식 안에서 BF16과 W4를 비교하며, graph W4를 eager BF16과 섞어 양자화 효과라고 부르지 않습니다.

{{speed_table}}

짝지은 독립 서버 3라운드의 기술통계 구간입니다. Eager의 처리량 구간은 1을 포함하므로 일관된 가속으로 단정하지 않습니다. KV 예산은 두 설정 모두 4 GiB입니다. 긴 입력·동시 요청 상한 32에서 preemption이 발생했으며, 상한이 항상 활성 sequence 32개를 뜻하지는 않습니다.

{{latency_table}}

이 표의 시간은 라운드별 중앙값(p50)의 평균이며 전체 요청을 합친 중앙값이 아닙니다. 포화 부하의 출력 처리량과 개인 요청의 지연 시간은 다르게 읽습니다. 측정 요청은 완료했지만 아래 별도 품질 실행의 종료 실패를 해소한 것은 아닙니다.

{{source_serving}}

정답과 정상 종료 여부 — Case009

ARC-Challenge는 예시 없이(0-shot), MMLU·GSM8K는 예시 5개(5-shot)를 사용했습니다. GSM8K는 greedy 생성·최대 1,024 token, WikiText-2는 rolling likelihood입니다. 품질 context는 8,192이며 위 고정 길이 속도 조건과 다릅니다.

{{quality_table}}

품질 저하가 남았습니다. 과제별로 방향이 다르고, MMLU·GSM8K에는 정답 손실이 있습니다. GSM8K의 두 행은 같은 출력의 다른 추출 규칙으로 독립 표본이 아닙니다. 출력 길이와 추출 규칙도 결과에 영향을 줍니다.

FAILED는 계산·파일 저장 뒤 비정상 종료입니다. W4의 ARC·MMLU, 두 설정의 WikiText가 해당합니다. 보존된 전체 문항의 계산값을 검산했지만 정상 완료로 바꾸지 않았습니다. 원래 실패 split은 재실행하지 않았고 원인은 미확정입니다.

실행 중 VRAM도 줄었는가? — Case009

RTX 5080 16GB에서 같은 모델의 BF16과 GPTQ W4A16을 비교했습니다. vLLM 0.29.0의 graph 실행, BF16 KV cache 예산 4 GiB를 두 설정에 공통으로 사용했습니다. 아래는 개별 요청이 아닌 서버 프로세스 전체 구간의 기록입니다.

시작·준비 실행(warmup)·바탕화면을 포함한 GPU 전체 사용량을 1초 간격으로 읽었습니다. 순간적인 최고 사용량을 놓칠 수 있고, 모델만의 VRAM이나 PyTorch 할당 메모리의 최고값과는 다릅니다.

각 수치는 소수 둘째 자리(GiB), 감소율은 소수 첫째 자리로 반올림했습니다. 요청 길이·동시성별 메모리 곡선과 최대 수용량은 측정하지 않았으므로, 다른 요청 조건에서도 같은 감소율을 보장하지 않습니다. 파일 크기와 GPU 메모리를 구분하는 법

라운드별 원기록과 감소율 계산 {{memory_pairs_table}}

같은 라운드의 BF16에서 W4를 뺀 뒤 BF16으로 나눠 감소율을 계산했습니다. 서로 다른 라운드의 최솟값·최댓값을 빼서 만든 감소율이나 통계적 신뢰구간이 아닙니다. MiB는 2²⁰ B, GiB는 2³⁰ B이며 1,024 MiB = 1 GiB입니다. 정확한 입력값과 계산값은 아래 공개 스칼라 JSON의 device_memory에 있습니다.

수치가 가까워져도 답변이 좋아지는가? — Case013

{{reference_table}}

문장에 준 확률 점수(PPL)와 원본 분포와의 차이(KL), 가중치 평균제곱오차(MSE)는 서로 다른 진단입니다. 4B에서 D16은 RTN보다 가중치 MSE·KL이 작아도 PPL은 높았습니다. 같은 32구간을 재사용한 진단이며 전체 benchmark 점수가 아닙니다. Case009의 단어 분모 PPL과는 입력·분모가 달라 값을 직접 비교하지 않습니다.

등록되지 않은 이름을 호출해 작업이 실행되지 않았습니다 — Case013 후속

가중치만 4비트로 바꾼 실험 변형 D16은 apply_fixture_patch 대신 대소문자가 다른 이름을 호출했습니다. 인자가 맞아도 도구는 실행되지 않았습니다. 성공이라는 최종 JSON만 보면 놓치는 문제였습니다.

직접 구현한 완화책은 등록된 이름만 생성하게 하는 출력 제약(ENUM)과, 이름 오류에 실제 등록명을 알려주는 오류 피드백(FEEDBACK)입니다. 호출 여부·인자·최종 답을 정답으로 덮어쓰지 않았습니다. 실제 fixture 수정과 성공한 validation 이벤트를 채점했습니다.

이름 제약은 ASCII 등록명·batch 1을 지원합니다. 이름/key의 escape 표기와 미지원 tokenizer 구성은 거절합니다. 생성 시간에는 CPU 제약 비용도 포함되며 서빙 TTFT나 packed kernel 속도가 아닙니다.
