Qwen3-4B-Instruct-2507: 실행한 작업과 확인된 한계

작게 저장한 모델이 다시 실행되는지, 빨라지는지, 업무까지 수행하는지 따로 확인했습니다.

제가 구현한 작업은 모델 파일을 줄여 다시 실행하는 절차, 응답 시간과 답변의 비교, AI 도구 사용 실패의 검사와 완화입니다. 아래는 RTX 5080 16GB에서 남긴 기존 기록입니다. BF16은 원래 16비트 숫자를 쓰는 비교 기준입니다. W4A16은 학습된 숫자(가중치)는 4비트, 각 계산 단계에 들어가는 값(활성값)은 16비트로 다룬다는 뜻입니다.

한눈에 보는 결론판단 범위모델·환경실행·재확인결과문제·완화구현·출처원자료·이력

1. 한눈에 보는 결론

  • 실제 저비트 실행 확인 — GPTQ W4A16. Case008 Q에서 압축한 모델 파일을 검사·복사하고, 모델 실행 프로그램(vLLM)을 새로 시작해 압축 가중치를 처리하는 GPU 코드(Marlin)가 선택된 기록을 확인했습니다. 가중치 파일 크기는 {{weight_files}}로 {{file_reduction}} 감소했습니다. 전체 그래픽카드 전용 메모리(VRAM)의 감소율은 아닙니다.
  • 요청 처리 이득을 조건별로 확인 — Case009. 같은 GPTQ 저장본도 요청 조건에 따라 이득이 달랐습니다. 미리 준비한 GPU 작업 묶음을 재사용하는 graph 실행의 출력 처리량비는 입력 128·동시 요청 상한 1에서 {{speed_small}}배, 입력 1024·상한 32에서 {{speed_large}}배입니다. 출력은 256 token으로 고정했습니다. 품질 저하와 종료 실패도 함께 확인해야 합니다.
  • 실행 중 VRAM 표본도 감소 — Case009. 같은 라운드끼리 비교한 GPU 전체 메모리의 최고 표본값은 {{memory_saved_percent}} 낮았습니다. {{memory_rounds}}라운드의 1초 간격 표본이며, 파일 크기 감소율과 다른 지표입니다. 실행 중 메모리 수치와 측정 조건
  • 품질 진단 경로 — Case013과 후속. 프로젝트에서 공개 수식을 바탕으로 구현한 비교용 변형(reference variant)의 숫자를 4비트 정수(INT4)로 줄인 뒤 16비트 형식(BF16)으로 복원해 계산했습니다. D16은 INT4 가중치와 BF16 입력값을, D4는 같은 가중치에 입력값도 INT4로 줄였다가 BF16으로 복원한 값을 씁니다. 모델 크기가 다른 두 모델이 아니며, 압축 표현을 직접 쓰는 실행(packed INT4)의 가속 결과도 아닙니다.
  • 남은 문제. Case013의 압축 실행(packed) 전체 모델 계산값 검사는 상대 오차 {{packed_error}}로 기준 {{packed_threshold}}를 넘었습니다. 일부 Case009 품질 프로세스는 계산 후 정상 종료하지 못했습니다. 별도 입력의 도구 작업 일반화와 장기 운영 안정성은 확인하지 않았습니다.

2. 이 자료로 판단할 수 있는 것

같은 장치에서 실제 실행된 저장 형식, 압축 파일의 검사·재로딩 절차, 같은 요청 조건의 비용 차이, 관측된 답변·도구 실패를 확인할 수 있습니다. 모델 변경 전에 어떤 항목을 다시 측정할지도 정할 수 있습니다.

다른 16GB GPU의 호환성, 모든 INT4나 DualQuant의 품질, 자신의 업무 정확도, 최대 안정 문맥 길이, 상용 운영 안정성은 판단할 수 없습니다. 개발과 실패 관찰에 사용한 작은 과제 집합(DEV)의 회복은 별도 입력의 검증을 대신하지 않습니다.

4. 검증한 설정과 실행·재확인 방법

GPU가 없어도 할 수 있는 일: 공개 파일이 기록된 해시와 같은지, 저장된 수치의 집계가 맞는지 CPU로 재확인합니다. 아래 명령은 모델을 다운로드하거나 실행하지 않습니다. 저장소 루트와 새 외부 출력 경로를 사용합니다.

새 출력의 summary.json과 검산 결과를 원자료와 비교합니다. 마지막 옵션은 공개본에 없는 외부 모델·기존 연구 원본을 이번 CPU 검사에서 확인하지 않았다는 뜻입니다. 원 실행 당시 외부 파일 보존을 확인한 기록(receipt)과는 별개입니다.

무작위 작은 모델의 CPU 저장·재로딩 예제도 있습니다. 학습된 Qwen3-4B 품질 결과와는 다른 기능 검사입니다.

기존 모델과 실행 환경이 있다면

  1. 모델 버전(revision)과 저장 파일의 해시(checksum) 확인
  2. 저장 형식·숫자 배열(tensor)·배열 크기(shape) 검사
  3. 별도 디렉터리로 복사
  4. 프로그램을 새로 시작해 짧은 동작 확인(smoke) 실행
  5. 압축 가중치를 쓰는 실행 코드 확인 후 자신의 업무 정답 비교

Case008 Q: 변환 → 저장본 작성 마무리 → 복사 → 검사 → 새 프로그램에서 짧은 실행 확인를 따릅니다. finalize는 Python 함수이며 별도 CLI 명령으로 만들지 않았습니다. Q에는 evaluate --track Q --split smoke를 사용하고, 일반 숫자 배열(dense) 저장본에만 쓰는 reload-test와 구분합니다.

Case009: 같은 모델 파일로 요청 처리와 정답 평가 다시 확인하기에는 원래 실행 환경과 비공개 설정(private-config) 항목이 있습니다. 4비트 가중치 파일(W4 artifact)이 없으면 중단하는 절차입니다. 공개 ZIP에는 GPU 재현에 필요한 실제 모델 데이터(payload)가 모두 들어 있지 않습니다.

숫자를 복원한 비교용 계산(reference)의 품질 진단은 Case013 재현 안내, 출력 제약은 후속 실행 안내와 범위로 연결합니다. 이번 안내서 구현에서는 이 GPU 명령들을 실행하지 않았습니다.

5. 품질·속도·메모리 결과

측정 방법과 결과 읽는 법을 공통 기준으로 사용합니다. 아래 표끼리는 서로 다른 실험 조건이므로 하나의 성능 점수로 합산하지 않습니다.

가중치 파일과 실행 중 메모리 — Case008 Q

{{storage_table}}

GB는 10⁹ B, GiB는 2³⁰ B입니다. 가중치 파일은 {{file_reduction}} 감소했습니다. PyTorch 계산용 메모리의 최고값(Torch allocator peak)은 초기화·캐시·실행을 포함한 별도 측정이며 GPU 전체 사용량은 아닙니다. 저장하고 프로그램을 새로 시작해 실행하는 과정은 확인했지만, GPU 작업을 그때그때 지시하는 eager 방식의 짧은 요청에서는 속도 우위를 확인하지 못했습니다.

{{source_bf16_files}} · {{source_storage}} · 원래 192개 합성 평가 입력의 품질·8토큰 시간 결과

조건별 출력 처리량 — Case009

CUDA graph는 반복되는 GPU 작업의 실행 준비 비용을 줄이는 방식입니다. Eager는 작업을 그때그때 실행하는 대조 조건입니다. 각 방식 안에서 BF16과 W4를 비교하며, graph W4를 eager BF16과 섞어 양자화 효과라고 부르지 않습니다.

{{speed_table}}

같은 조건의 원본·압축 모델 서버를 한 묶음(paired)으로 실행한 3라운드의 통계 구간입니다. Eager의 처리량 구간은 1을 포함하므로 일관된 가속으로 단정하지 않습니다. 이전 문장의 계산을 보관하는 KV 캐시 예산은 두 설정 모두 4 GiB입니다. 긴 입력·동시 요청 상한 32에서는 진행 중인 요청을 잠시 중단하는 일(preemption)이 있었으며, 32개가 늘 동시에 계산된다는 뜻은 아닙니다.

{{latency_table}}

이 표의 시간은 라운드별 중앙값(p50)의 평균이며 전체 요청을 합친 중앙값이 아닙니다. 요청을 계속 채워 넣는 포화 부하의 출력 처리량과 개인 요청의 지연 시간은 다르게 읽습니다. 측정 요청은 완료했지만 아래 별도 품질 실행의 종료 실패를 해소한 것은 아닙니다.

{{source_serving}}

정답과 정상 종료 여부 — Case009

ARC-Challenge는 예시 없이(0-shot), MMLU·GSM8K는 예시 5개(5-shot)를 사용했습니다. GSM8K는 매번 가장 높은 확률의 다음 조각을 고르는 생성(greedy)·최대 1,024 token, WikiText-2는 긴 글을 나누어 다음 글자·단어 조각에 준 확률을 계산하는 방식(rolling likelihood)입니다. 품질 평가의 최대 입력·출력 범위(context)는 8,192이며 위 고정 길이 속도 조건과 다릅니다.

{{quality_table}}

품질 저하가 남았습니다. 과제별로 방향이 다르고, MMLU·GSM8K에는 정답 손실이 있습니다. GSM8K의 두 행은 같은 출력의 다른 추출 규칙으로 독립 표본이 아닙니다. 출력 길이와 추출 규칙도 결과에 영향을 줍니다.

FAILED는 계산·파일 저장 뒤 비정상 종료입니다. W4의 ARC·MMLU, 두 설정의 WikiText가 해당합니다. 보존된 전체 문항의 계산값을 검산했지만 정상 완료로 바꾸지 않았습니다. 원래 실패한 평가 묶음(split)은 재실행하지 않았고 원인은 미확정입니다.

등록되지 않은 이름을 호출해 작업이 실행되지 않았습니다 — Case013 후속

가중치를 INT4로 저장하고 BF16으로 복원하며 입력값은 BF16으로 쓰는 변형 D16은 apply_fixture_patch 대신 대소문자가 다른 이름을 호출했습니다. 인자가 맞아도 도구는 실행되지 않았습니다. 성공이라는 최종 JSON만 보면 놓치는 문제였습니다.

직접 구현한 완화책은 등록된 이름만 생성하게 하는 출력 제약(ENUM)과, 이름 오류에 실제 등록명을 알려주는 오류 피드백(FEEDBACK)입니다. 호출 여부·인자·최종 답을 정답으로 덮어쓰지 않았습니다. 실제 예제 파일(fixture)의 수정과 성공한 검사(validation) 기록을 채점했습니다.

이름 제약은 영문 문자 중심(ASCII)의 등록명·한 번에 입력 하나(batch 1)을 지원합니다. 이름과 필드명(key)의 이스케이프 표기와 지원하지 않는 문장 분할기(tokenizer) 구성은 거절합니다. 생성 시간에는 CPU에서 이름을 제한하는 비용도 포함됩니다. 서비스의 첫 응답 시간(TTFT)이나 압축 가중치 계산 코드(packed kernel)의 속도를 측정한 값은 아닙니다.

{{repair_table}}

개발·실패 분석에 이미 썼던 문제(DEV) {{dev_tasks}}개를 재사용했습니다. {{episodes}}개의 실행 기록(episode)은 같은 문제의 {{logical_conditions}}개 조건이며 서로 다른 문제가 {{episodes}}개라는 뜻은 아닙니다. D4는 D16과 같은 INT4 가중치에 입력값도 INT4로 줄였다 복원하며, 결합 조건에서도 {{d4_remaining}}개 실패가 남았습니다.

ENUM과 BOTH(이름 제한+피드백)의 결과는 같았습니다. 따라서 이름 제한에 피드백을 더한 추가 효과는 입증하지 못했습니다. 이 결과는 이 프로젝트의 비교용 변형(reference variant)과 기존 개발 문제(DEV)에 한정한 실행 오류 완화입니다. 양자화 수치오차의 복구, 모든 DualQuant·INT4의 품질, 별도 입력의 일반화나 packed 가속의 증거는 아닙니다.

7. 직접 구현한 부분과 외부 기술

DIOVA의 작업은 숫자 변환·저장·다시 실행하기를 연결하고, 같은 입력의 수치·답변·도구 행동을 비교하는 코드입니다. GPTQ, 원형 모델, 모델 요청 처리 프로그램(서빙 엔진)과 압축 가중치용 GPU 계산 코드(저비트 kernel) 자체의 기여는 외부 저자에게 있습니다.

  • 숫자 변환과 저장 파일 검사: GPTQ 변환 연결 · 저장 파일 마무리(finalize)·검사 · 저장·재실행 오류를 검사하는 테스트
  • 요청과 품질 비교: 모델 요청 실행기 · 기존 정답 평가 프로그램 연결 · 입력·실행 규칙 테스트 · CPU 답변 비교 도구와 입력 형식
  • 비교용(reference) 숫자 변환·계산·검산: 4비트 보정값 계산·모델 연결(INT4 solver·adapter) · 4비트 숫자를 묶어 저장(packed) · 저장 수치·출처 검산 · 기록 일치·오류 검사 테스트
  • 도구 이름 제약과 오류 피드백: 등록된 도구 이름만 허용하는 코드(guard) · 기능 테스트 · 실제 실행 기록·정답 조건 검산
