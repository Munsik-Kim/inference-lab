대표작 B · DIOVA-COMPARE · CPU 합성 예제

같은 질문에서 달라진 답변 확인하기

제가 만든 비교 도구에 저장된 답변 파일 두 개를 넣으면, 어떤 질문을 새롭게 틀렸고 맞혔는지 보고서로 볼 수 있습니다.

모델 교체나 압축 전후의 결과 검토에 사용할 수 있습니다. 사용자가 모델 실행과 답변 채점을 먼저 마친 뒤 사용합니다. AI 모델 실행, 자유 서술 답변의 범용 자동 채점, 원자료 진위 인증은 이 도구의 역할이 아닙니다. 아래 공개 합성 예제는 synthetic_test이며 GPU 실측이나 실제 모델 우열의 근거가 아닙니다.

실행보고서내 기록거절 예기술적 판단짧은 시연

1. 두 파일 준비 → 형식 검사(validate) → 비교(compare)

변경 전 결과(baseline) JSONL 받기 · 변경 후 결과(candidate) JSONL 받기. JSONL은 한 줄에 질문 하나의 결과를 담는 텍스트 파일입니다. 전체 저장소를 받은 뒤 루트에서 Python 3.10 이상으로 실행하세요. 매번 새 전용 환경과 출력 경로를 사용합니다.

EXAMPLE_ROOT=$(mktemp -d)
python3 -m venv "$EXAMPLE_ROOT/venv"
"$EXAMPLE_ROOT/venv/bin/python" -m pip install --no-deps ./packages/diova-compare
"$EXAMPLE_ROOT/venv/bin/diova-compare" validate --input packages/diova-compare/examples/compare/baseline.jsonl
"$EXAMPLE_ROOT/venv/bin/diova-compare" validate --input packages/diova-compare/examples/compare/candidate.jsonl
"$EXAMPLE_ROOT/venv/bin/diova-compare" compare --baseline packages/diova-compare/examples/compare/baseline.jsonl --candidate packages/diova-compare/examples/compare/candidate.jsonl --output "$EXAMPLE_ROOT/report"

예상 결과는 각 validate의 status: PASS, records: 4와 compare의 status: PASS, n_pairs: 4, 종료 코드 0입니다. PASS는 입력 형식 검사와 비교가 끝났다는 뜻이며, 모델 답변이 모두 정답이라는 뜻은 아닙니다. 세 보고서 파일을 생성합니다. 모델·Torch·CUDA·NumPy는 필요하지 않습니다. 설치 과정에서 Python 빌드 도구를 가져올 수 있습니다.

명령은 Linux/macOS 기준입니다. Windows에서는 별도 Python 환경에서 같은 CLI 인자를 사용합니다. 전체 명령·입력 문장·정답 규칙

2. 정답률이 같아도 잃은 답을 찾습니다

정답은 기준선 답변을 복사하지 않고 두 정수의 합으로 정했습니다. 답은 공백을 제거한 십진 정수 문자열입니다.

공개 합성 네 쌍 · 실제 모델 측정과 별도
ID · 질문정답기준선 → 후보읽는 법
sum-01 · 2 + 244 → 5정답 손실
sum-02 · 3 + 587 → 8새 정답
sum-03 · 6 + 176 → 9다른 오답
sum-04 · 4 + 599 → 9둘 다 정답

양쪽 정답은 2/4입니다. 이전에 맞혔다가 틀린 답 correct_to_wrong=1, 새로 맞힌 답 wrong_to_correct=1, 다른 오답으로 바뀐 답 wrong_to_wrong=1, 전체 답변 변경 all_answer_disagreement=3으로 같은 평균 속의 변화를 나눕니다.

  • report.md: 과제별 요약부터 읽기.
  • report.json: 실행 설정, 집계와 모든 입력 쌍 확인.
  • pairs.csv: 어떤 질문에서 잃거나 회복했는지 행별 확인.

네 개의 합성 입력으로 계산한 통계 구간은 이 예제의 요약이며, 모델 우열이나 실제 업무의 일반화 근거가 아닙니다.

3. 자신의 저장된 결과로 바꾸기

모델을 두 설정으로 실행한 기록, 각 질문의 허용 정답, 답을 추출하고 채점한 규칙을 준비합니다. 자유 서술형 답변의 맞음·틀림은 사용자가 제공해야 합니다. 아래 필드를 채운 JSONL 두 개를 각각 validate한 다음 compare에 파일 경로를 넣으세요.

내 기록 → 현재 입력 형식(schema version 1)
내 기록필드같게 맞추거나 제공할 내용
평가셋·질문 IDtask, task_version, sample_id양쪽 같은 입력을 식별
실제 입력prompt_hash시스템 지시·질문 틀까지 같은 방식으로 담은 입력의 확인용 문자열(UTF-8 SHA256)
독립 정답·채점 규칙gold, gold_definition허용 답 목록·추출·정규화 정의가 같아야 함
모델·저장본model_id, artifact_id각 파일 안에서 하나의 모델/저장본 조합
추출 답·정오output_type, answer, correct자유 서술은 extracted_answer; correct의 true/false 판정은 사용자가 제공
자료 종류·형식evidence_kind, schema_version실측 measurement / 과거 기록 historical / 합성 예제 synthetic_test; 형식 버전은 정수 1
선택: 원 실행 종료 코드process_exit_code양쪽 모든 행에 정수로 제공하거나 모두 생략

hash 계산은 hashlib.sha256(prompt.encode("utf-8")).hexdigest()입니다. CLI는 식별자의 일치를 검사하며 실제 입력 원문이나 저장 모델 파일(artifact)의 내용이 진짜인지 인증하지 않습니다. 자유 생성의 정오도 입력받으므로 범용 자동 채점기가 아닙니다.

답변 비교만 할 때 distribution과 scores는 생략할 수 있습니다. 전체 단어 후보의 확률이나 모델 원점수(logits)는 필요하지 않습니다. 선택지별 확률을 추가하면 정답에 준 확률의 손실(NLL)과 확률 예측 오차(Brier)를, 서로 맞는 확률 분포가 있으면 원본과의 차이(KL)를 계산합니다. 원 실행 종료 코드는 보고서에 보존됩니다.

공개 가능한 입력만 공유 예제·보고서에 넣으세요. 파일은 로컬 CLI에서 읽고 브라우저나 원격 서비스에 업로드하는 단계는 없습니다.

4. 다른 질문은 모델 변경 효과로 집계하지 않습니다

후보 파일의 첫 prompt_hash만 "0" * 64로 바꾼 복사본은 단독 validate를 통과해도 compare에서 pair mismatch: prompt_hash로 거절됩니다. 종료 코드 2이며 보고서 디렉터리를 만들지 않습니다. 정답 규칙만 다르면 pair mismatch: gold_definition입니다.

의도적인 불일치 실행 명령
"$EXAMPLE_ROOT/venv/bin/python" - "$EXAMPLE_ROOT/mismatch.jsonl" <<'PY'
import json, sys
from pathlib import Path
rows = [json.loads(line) for line in Path("packages/diova-compare/examples/compare/candidate.jsonl").read_text().splitlines()]
rows[0]["prompt_hash"] = "0" * 64
Path(sys.argv[1]).write_text("".join(json.dumps(row) + "\n" for row in rows))
PY
"$EXAMPLE_ROOT/venv/bin/diova-compare" compare --baseline packages/diova-compare/examples/compare/baseline.jsonl --candidate "$EXAMPLE_ROOT/mismatch.jsonl" --output "$EXAMPLE_ROOT/rejected-report"

--intersection은 공통 ID만 비교하는 명시적 옵션이며 달라진 질문·채점 규칙을 일치시키는 수단이 아닙니다.

5. 이렇게 만들었고, 여기까지 확인합니다

  • 선택: 평균과 함께 입력별 정답 손실·회복을 나누고 원 실행 실패 상태를 남깁니다.
  • 대안: 평균 정답률만 비교하면 이 예제처럼 이전에 맞혔던 문제를 틀리게 된 변화가 가려집니다.
  • 근거: 실제 집계 코드와 정답 변화·입력 짝 검사(pairing)·실패 보존 테스트에서 어떤 입력을 받고 어떻게 집계하는지 확인할 수 있습니다.
  • 한계·다음 기준: 새 업무에 적용하려면 사용자가 제공한 채점 기준과 같은 질문을 식별하는 규칙부터 확인해야 합니다. 현재 설계 설명이며 당시 대안 실험을 추가로 주장하지 않습니다.

6. 60–90초 시연 동선

  1. 같은 정답률도 개별 손실을 숨긴다는 문제를 소개합니다.
  2. 위 두 파일의 validate와 compare를 실제로 실행합니다. CPU 합성 예제라고 밝힙니다.
  3. 생성된 report.md와 pairs.csv에서 sum-01의 손실, sum-02의 회복을 확인합니다.
  4. 연결된 코드와 테스트에서 입력 거절·실패 보존의 근거를 엽니다.

영상 플레이어가 아니라 실행 가능한 시연 안내입니다. 기존 GPU 실험 기록을 읽으려면 Case009 품질 기록과 Case013 후속으로 별도 구분합니다.
